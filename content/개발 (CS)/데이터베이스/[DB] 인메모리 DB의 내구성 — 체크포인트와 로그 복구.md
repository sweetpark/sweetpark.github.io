## 📌 한눈에 보기 — 주의해야 할 점

메모리는 **빠르지만 전원이 꺼지면 사라진다.** 그래서 메모리 DB는 "빠름"을 지키면서 "안 잃음"을 얻기 위해 **디스크에 두 가지**를 따로 남긴다.

| # | 규칙 | 이유 | 상세 |
|---|---|---|---|
| 1 | 디스크에 **체크포인트(스냅샷) + 변경 로그** 둘을 남긴다 | 복구 = 스냅샷 읽기 + 그 뒤 로그 되감기 | [§2](#2-두-가지를-디스크에-남긴다) |
| 2 | **로그를 먼저** 쓰고 나서 메모리를 바꾼 것으로 친다 (WAL) | 메모리만 바뀐 채 죽으면 변경이 흔적도 없이 사라진다 | [§3](#3-로그를-먼저-쓴다-wal) |
| 3 | "커밋됨" = 커밋 로그가 **디스크에 안전하게 닿았다**는 뜻 | `write()` 만으론 OS 캐시에 있을 뿐 | [§4](#4-커밋과-flush--빠름과-안전의-교환) |
| 4 | flush 를 **얼마나 자주** 할지는 정책이다 | 매번 하면 안전하지만 느리고, 모아서 하면 빠르지만 최근 몇 건을 잃을 수 있다 | [§4](#4-커밋과-flush--빠름과-안전의-교환) |
| 5 | 체크포인트를 **주기적으로** 한다 | 안 하면 로그가 끝없이 늘고 복구 시간도 끝없이 늘어난다 | [§5](#5-체크포인트는-왜-필요한가) |
| 6 | 공유메모리에 DB 가 있으면 **프로세스 크래시는** 견디지만 **전원 차단은** 못 견딘다 | 공유메모리는 프로세스의 것이 아니라 커널(RAM)의 것 | [§7](#7-공유메모리-위의-db) |
| 7 | 복제 지연은 **로그 번호(LSN) 차이**로 잰다 | 시간이 아니라 "몇 건 뒤처졌나" | [§6](#6-복제와-lsn) |
| 8 | **자동 커밋**이 켜져 있으면 `ROLLBACK` 은 돌릴 게 없다 | 문장 하나마다 이미 커밋됐다 | [§8](#8-자동-커밋의-함정) |

## 1. 왜 메모리에 두나

디스크 DB 는 데이터를 읽을 때마다 디스크(또는 그 캐시)를 거친다. 메모리 DB 는 **전체 데이터가 처음부터 RAM 에** 있어서 읽기·쓰기가 포인터 따라가기 수준이다.

| | 디스크 DB | 메모리 DB |
|---|---|---|
| 읽기/쓰기 지연 | 디스크 접근이 낄 수 있다 (캐시 미스) | 거의 메모리 속도 |
| 용량 한계 | 디스크 크기 | **RAM 크기** |
| 전원이 꺼지면 | 데이터는 디스크에 남아 있다 | **그대로면 전부 사라진다** |

통신·과금처럼 **지연이 짧아야 하는 시스템**이 메모리 DB 를 쓴다. 대가는 "사라지는 문제"를 직접 풀어야 한다는 점이다.

---

## 2. 두 가지를 디스크에 남긴다

도서관 장부에 비유하면:

- **스냅샷(체크포인트)**: 어느 날 밤, 모든 책의 상태를 **통째로 새 장부에 베껴 적는다.** 베끼는 데 시간이 걸린다.
- **변경 로그**: 그날 이후 일어난 일을 **한 줄씩 순서대로 덧붙여 적는다.** ("A 책 대출", "B 책 반납"…) 한 줄은 금방 쓴다.

장부가 불타 사라진 뒤 복구하려면?

```
복구 = 마지막 스냅샷을 읽는다
     + 그 스냅샷 이후의 로그를 처음부터 끝까지 다시 실행한다(replay)
```

로그의 각 줄에는 **번호**(LSN: Log Sequence Number)가 붙고, 번호는 계속 커진다.

```
스냅샷 (LSN 1000 까지 반영) ─▶ 로그: 1001, 1002, 1003, … 1250  (여기서 서버가 죽음)
복구: 스냅샷 로드 → 1001~1250 을 순서대로 재실행 → 죽기 직전 상태로 돌아옴
```

## 3. 로그를 먼저 쓴다 (WAL)

**WAL = Write-Ahead Logging, "앞서 쓰는 로그".** 규칙은 하나다.

> 메모리의 데이터를 바꾸기 **전에**(적어도 "바꿨다고 응답하기 전에") 그 변경을 설명하는 **로그를 디스크에 먼저** 남긴다.

왜 이 순서인가? 반대로 하면:

```
1. 메모리를 바꾼다 ─▶ 2. (여기서 크래시) ─▶ 3. 로그를 쓴다 (못 씀)
   → 로그에도 스냅샷에도 흔적이 없다. 그런데 클라이언트에게는 "성공"이라고 말했을 수 있다.
```

로그를 먼저 쓰면 크래시 후 로그를 재생해서 **언제나 따라잡을 수 있다.** 로그는 이어 붙이기만 하므로(append-only) 디스크 쓰기도 순차 쓰기라 빠르다.

---

## 4. 커밋과 flush — 빠름과 안전의 교환

"로그를 디스크에 썼다"는 말은 생각보다 모호하다.

```
 프로그램 ─write()▶ [ OS 페이지 캐시 ] ──(나중에)──▶ [ 디스크 ]
                         ▲ 여기까지만 가면 write() 는 성공을 돌려준다
```

`write()` 가 돌아왔어도 **전원이 나가면 OS 캐시의 내용은 사라질 수 있다.** (프로세스가 `kill -9` 로 죽는 것은 괜찮다 — 이미 OS 캐시에 있으니까. 전원/커널 장애가 문제다.) 디스크에 **정말 닿게** 하려면 `fsync()` 계열 호출이 필요하고, 이게 느리다.

| 정책 | 방법 | 안전 | 속도 |
|---|---|---|---|
| **커밋마다 fsync** | 매 커밋마다 디스크에 닿을 때까지 기다림 | 커밋된 것은 절대 안 잃음 | 느림 |
| **그룹 커밋** | 여러 트랜잭션의 로그를 모아 한 번에 fsync | 거의 같음 | 빠름 |
| **주기적 flush** | 예: 100ms 마다 | 전원 장애 시 **최근 100ms 의 커밋을 잃을 수 있음** | 가장 빠름 |

어느 쪽이든 "잃을 수 있는 구간"을 **알고 정한** 것이 중요하다. 정하지 않은 기본값이 곧 정책이 된다.

## 5. 체크포인트는 왜 필요한가

로그만 있고 스냅샷이 없다면?

- 로그는 **끝없이 커진다** (디스크 낭비).
- 복구하려면 **서버를 처음 켠 날부터** 로그를 전부 다시 실행해야 한다 → 복구에 몇 시간.

체크포인트를 주기적으로 하면:

```
체크포인트 시점 T 에 스냅샷 완료 → T 이전의 로그는 더 이상 필요 없다 (보관하거나 지운다)
복구 시간 = 스냅샷 읽기 + (T 이후 로그만) 재실행
```

체크포인트 중에도 서비스는 계속된다. 그래서 스냅샷이 "정확히 한 순간"이 아닐 수 있고, 로그에 **"체크포인트가 시작된 지점"** 을 표시해서 어디서부터 재생해야 하는지 알게 한다.

> 복구 중 마지막 로그 한 줄이 **반쯤만 써진 채**일 수 있다(쓰는 도중 전원 차단). 로그 한 줄마다 **체크섬**(길이·검증값)을 붙여, 검증이 틀리면 거기서 멈추고 그 줄은 버린다.

## 6. 복제와 LSN

한 대가 죽어도 이어 가려고 **복제본**을 둔다. 복제의 기본 방식은 같은 로그를 복제본에게 보내 재생하는 것이다.

| 용어 | 뜻 |
|---|---|
| 주(primary)의 LSN | 주가 지금까지 만든 로그 번호 (예: 1250) |
| 복제본의 LSN | 복제본이 반영한 번호 (예: 1240) |
| **복제 지연** | 둘의 차이 = 1250 − 1240 = **10건** 뒤처짐 |

시간(초)이 아니라 **번호 차이**로 재는 이유: 주가 한가하면 시간은 많이 흘러도 차이는 0 이고, 바쁘면 1초에도 차이가 수천이 된다. **차이가 일정 값을 넘으면 알람**을 올리는 식으로 감시한다. 이 상태에서 주가 죽어 복제본이 승격되면 그 10건은 잃는다 — 복제를 **비동기**로 할 때의 대가다.

## 7. 공유메모리 위의 DB

메모리 DB 가 **공유메모리 세그먼트**에 데이터를 두는 구조라면, 프로세스와 전원의 두 장애에 대한 결과가 다르다.

| 장애 | 공유메모리 안의 데이터 |
|---|---|
| DB 데몬 프로세스가 `kill -9` 로 죽음 | **메모리는 남는다** (세그먼트는 커널 것). 하지만 **쓰던 중에 죽었다면 반쯤 바뀐 상태가 남을 수 있다.** → 락·복구 절차가 필요 |
| OS 재부팅 / 전원 차단 | **전부 사라진다** → 스냅샷 + 로그에서 복구 |

"프로세스가 죽어도 메모리는 있으니 괜찮다"는 절반만 맞다. **일관성**은 따로 보장해야 한다. (실습: P106 `shm_probe` 에서 프로세스가 죽어도 세그먼트가 남는 것을 직접 확인할 수 있다.)

## 8. 자동 커밋의 함정

**자동 커밋(autocommit)**: 문장 하나가 끝나는 순간 자동으로 커밋하는 모드.

| 모드 | `INSERT` 하고 `ROLLBACK` | 클라이언트가 커밋 전에 죽으면 |
|---|---|---|
| 자동 커밋 **켜짐** | 이미 커밋됐다 → **롤백이 아무 일도 안 한다.** 에러도 안 난다 | 이미 커밋된 문장은 남는다 |
| 자동 커밋 **꺼짐** | 취소된다 | 커밋 안 된 변경은 사라진다 |

여러 문장을 **하나의 단위로** 묶으려는 코드(예: 계좌 이체 — 출금과 입금)가 자동 커밋이 켜진 연결에서 돌면, 중간에 실패해도 앞 문장이 남아 **일부만 적용**된다. 코드가 트랜잭션 경계를 기대한다면 **자동 커밋이 꺼져 있는지** 확인해야 한다. 기본값이 서버마다 다를 수 있다는 점도 함정이다.

## 9. 정리

1. 메모리 DB 는 디스크에 **스냅샷 + 변경 로그**를 따로 남긴다. 복구 = 스냅샷 + 그 이후 로그 재생.
2. **로그를 먼저** 쓴다(WAL). "커밋됨"의 뜻은 정책(`fsync` 빈도)이 정한다.
3. 체크포인트가 없으면 로그와 복구 시간이 끝없이 늘어난다.
4. 복제 지연은 **LSN 차이**로, 자동 커밋은 **롤백을 무력화**한다.
