# 메시지 큐가 가득 차면 — 용량·EAGAIN·블로킹, 그리고 죽은 수신자

## 📌 한눈에 보기 — 주의해야 할 점

| # | 사실 | 결과 | 상세 |
|---|---|---|---|
| 1 | 큐는 **프로세스가 아니라 커널**이 들고 있다 | 받는 쪽이 죽어도 큐와 안의 메시지는 **그대로 남는다** | [§1](#1-큐는-누구-것인가) |
| 2 | 큐에는 **바이트 용량**이 있다 (`msg_qbytes`) | 개수가 아니라 *본문 길이의 합*으로 찬다 | [§2](#2-용량은-무엇으로-정해지나) |
| 3 | 가득 차면 `msgsnd` 는 **기본적으로 잠든다** | 보내는 프로세스가 멈춘 것처럼 보인다 | [§3](#3-가득-찼을-때-보내는-쪽에-일어나는-일) |
| 4 | `IPC_NOWAIT` 를 주면 **`EAGAIN`** 으로 즉시 돌아온다 | 버릴지 재시도할지 *호출자가* 정한다 | [§3](#3-가득-찼을-때-보내는-쪽에-일어나는-일) |
| 5 | 한 메시지 크기는 **`msgmax`** 를 못 넘는다 | 큐가 비어 있어도 `EINVAL` | [§2](#2-용량은-무엇으로-정해지나) |
| 6 | 큐를 안 지우면 **계속 남는다** | `ipcs -q` 로 보이고, 개수 한도(`msgmni`)를 갉아먹는다 | [§5](#5-직접-관찰하기) |
| 7 | 쌓인 양은 커널에게 **물어보면** 된다 | 직접 세지 않아도 `msgctl(IPC_STAT)` 한 번이면 된다 | [§4](#4-쌓인-양을-알아내는-법) |

## 1. 큐는 누구 것인가

우체통을 떠올려 보자. 우체통은 **우체국(커널)** 이 설치해 둔 것이다. 편지를 받을 사람이 이사를 가도(프로세스 종료) 우체통은 그 자리에 있고, 편지도 그대로 쌓여 있다.

```
 보내는 프로세스 ──msgsnd──▶ [ 커널 안의 큐 ] ──msgrcv──▶ 받는 프로세스
                              (프로세스와 무관하게 존재)
```

- 받는 프로세스가 죽어도 큐는 남는다 → **보내는 쪽은 계속 보낼 수 있고, 큐는 계속 찬다.**
- 보내는 프로세스가 죽어도(`kill -9` 포함) 이미 넣은 메시지는 남는다.
- 큐가 사라지는 경우는 `IPC_RMID`(`ipcrm -q`)로 지울 때, 그리고 재부팅뿐이다.

> 파일처럼 "열어 둔 프로세스가 모두 닫으면 사라진다"가 **아니다.** 이 점 때문에 정리 안 된 큐가 쌓인다.

## 2. 용량은 무엇으로 정해지나

| 이름 | 의미 | 리눅스에서 보는 곳 |
|---|---|---|
| `msg_qbytes` | **이 큐 하나**에 쌓을 수 있는 바이트 합 | `msgctl(IPC_STAT)` / `ipcs -q -l` |
| `msgmnb` | 큐를 만들 때 `msg_qbytes` 의 **기본값** | `/proc/sys/kernel/msgmnb` |
| `msgmax` | **메시지 한 개**의 최대 길이 | `/proc/sys/kernel/msgmax` |
| `msgmni` | 시스템 전체 **큐 개수** 한도 | `/proc/sys/kernel/msgmni` |

두 가지를 기억하면 된다.

1. **개수가 아니라 바이트로 찬다.** 100바이트 메시지는 `msg_qbytes ÷ 100` 개, 8000바이트 메시지는 훨씬 적게 들어간다. (직접 재 보면 `mtype` 8바이트는 세지 않고 **본문 길이만** 더해진다.)
2. 큐의 용량을 **올리는 것은 특권(root)** 이 필요하다. 줄이는 것은 누구나 할 수 있다. 그래서 대용량 큐가 필요한 시스템은 `msgmnb` 를 미리 키워 둔다.

수치 예 — 리눅스 기본 `msgmnb = 16384`, `msgmax = 8192`일 때:

| 메시지 길이 | 들어가는 개수 |
|---|---|
| 100 B | 163개 (16384 ÷ 100) |
| 8000 B | 2개 |
| 8193 B | 0개 — 비어 있어도 `EINVAL` (`msgmax` 초과) |

## 3. 가득 찼을 때 보내는 쪽에 일어나는 일

| `msgsnd` 의 flags | 큐가 가득 찼을 때 | 언제 쓰나 |
|---|---|---|
| `0` (기본) | **호출이 잠든다.** 누군가 `msgrcv` 로 공간을 만들어 줄 때까지 | 받는 쪽이 반드시 따라잡는다고 확신할 때 |
| `IPC_NOWAIT` | 즉시 `-1`, `errno = EAGAIN` | 서비스가 멈추면 안 될 때 |

기본값이 "잠듦"이라는 점이 사고의 원인이 된다.

> 받는 프로세스가 죽는다 → 큐가 찬다 → 보내는 프로세스가 `msgsnd` 에서 영원히 잠든다 → **보내는 프로세스도 같이 멈춘다** → 그 프로세스에게 보내던 또 다른 프로세스도…

연쇄로 퍼진다. 이걸 끊는 방법이 `IPC_NOWAIT` 다. `EAGAIN` 을 받으면 선택지가 생긴다.

| 선택 | 의미 |
|---|---|
| 버린다 (+ 버린 개수를 센다) | [비동기 로깅](개발%20%28CS%29/언어/C언어/동시성·스레드/[C]%20비동기%20로깅과%20링%20버퍼%20—%20큐가%20가득%20차면%20어떻게%20되나.md)과 같은 정책 |
| 잠깐 쉬고 재시도 | 일시적 정체일 때 |
| 에러로 올려 보낸다 | 상위가 판단하게 |

## 4. 쌓인 양을 알아내는 법

`msgctl(qid, IPC_STAT, &ds)` 가 돌려주는 구조체에 다 있다.

| 필드 | 의미 | 쓰임 |
|---|---|---|
| `msg_qnum` | 지금 쌓인 메시지 **개수** | "얼마나 밀렸나" |
| `__msg_cbytes` | 지금 쌓인 **바이트** | 사용률 = `cbytes ÷ qbytes` |
| `msg_qbytes` | 이 큐의 **용량** | 분모 |
| `msg_lspid` / `msg_lrpid` | 마지막으로 보낸/받은 프로세스 PID | "누가 안 읽고 있나" |

큐를 직접 구현했다면(공유메모리 위의 링 버퍼) `head`/`tail` 을 읽어서 직접 계산해야 한다. 커널 큐는 **커널에게 물어보면 된다**는 점이 큰 이점이다. 사용률로 경보를 올리는 도구들(예: 80%/90%/100% 단계)이 대개 이 값으로 계산한다.

## 5. 직접 관찰하기

```bash
ipcs -q            # 시스템의 모든 큐: used-bytes, messages 열이 쌓인 양
ipcs -q -l         # 한도 (max size of message / default max size of queue / max queues)
ipcrm -q <msqid>   # 큐 삭제 (쌓인 메시지도 함께 사라진다)
```

`P105 msgq_probe` 드릴이 이 관찰을 코드로 해 보는 문제다. 정리하면 이런 장면들이 나온다.

| 장면 | 보이는 것 |
|---|---|
| 용량 4096 큐에 100B 를 가득 채움 | 40개에서 `EAGAIN`. 이어서 96B 는 들어가고 1B 는 `EAGAIN` (남은 공간이 정확히 0) |
| 보내던 프로세스를 `kill -9` | `ipcs -q` 에서 메시지가 그대로 남아 있음 |
| 큐를 안 지우고 프로그램 종료 | `ipcs -q` 에 큐가 계속 남음 (key 가 `0x00000000` 이면 `IPC_PRIVATE` 로 만든 것) |

---

## 6. 정리

1. 큐는 커널 것이다 — **누가 죽어도 남는다.** 그래서 정리는 명시적으로 해야 한다.
2. 용량은 **바이트**이고, 메시지 하나의 최대 길이도 따로 있다.
3. 가득 차면 기본은 **잠듦**. 서비스를 멈추고 싶지 않다면 `IPC_NOWAIT` + `EAGAIN` 처리.
4. 쌓인 양은 커널에 묻는다 (`IPC_STAT`). 사용률로 경보를 만들 수 있다.
