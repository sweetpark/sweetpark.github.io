## 1. 로그와 알람은 다르다

| | 로그 | 알람 |
|---|---|---|
| 성격 | "이런 일이 **일어났다**" (사건) | "지금 **이런 상태다**" (상태) |
| 끝이 있나 | 없다 (한 줄 적고 끝) | **있다** (해제되면 끝) |
| 질문 | 무슨 일이 있었나? | **지금** 문제가 있나? |

로그는 `큐가 90%를 넘었음` 한 줄이면 되지만, 알람은 **"넘은 상태가 이어지는 동안 켜져 있다가, 정상이 되면 꺼져야"** 한다. 그래서 알람 시스템은 알람마다 현재 상태를 기억한다.

---

## 2. 상태 머신으로 본다

```
            조건 충족                     조건 해소
  ┌────────┐ ────────▶ ┌──────────────┐ ────────▶ ┌────────┐
  │ NORMAL │           │ ALARM (켜짐) │           │ NORMAL │
  └────────┘ ◀──────── └──────────────┘           └────────┘
        발생(OCCURRED) 알람 한 번        해제(CLEARED) 알람 한 번
```

- **상태가 바뀔 때만** 알람을 낸다. `NORMAL → ALARM` 에서 "발생" 한 번, `ALARM → NORMAL` 에서 "해제" 한 번.
- 이미 `ALARM` 인데 조건이 계속 충족돼도 **다시 내지 않는다.**
- 해제를 낼 때는 해제 시점의 수치(예: 현재 사용률)를 같이 적으면 운영자가 판단하기 쉽다.

---

## 3. 임계 하나의 문제 — 깜박임 (flapping)

"사용률 90% 넘으면 켜고, 90% 이하면 끈다"로 만들면 어떻게 될까? 사용률이 임계 근처에서 흔들린다고 하자.

```
측정 :  88   91   89   92   89   91   88
단일 임계(90):
상태 :  OK  ALARM OK  ALARM OK  ALARM OK
알람 :       발생  해제  발생  해제  발생  해제   ← 7번 측정에 알람 6건
```

운영자 입장에서는 같은 문제가 "났다 풀렸다"를 반복하는 것이라 **무엇을 해야 하는지 알 수 없다.** 이게 **flapping** 이다.

---

## 4. 해법 1 — 히스테리시스

켤 때와 끌 때의 기준을 **다르게** 둔다.

```
켜는 기준: 90% 초과       끄는 기준: 80% 미만
 (그 사이 80~90%는 "지금 상태를 유지")

측정 :  88   91   89   92   89   91   88   79
상태 :  OK  ALARM ALARM ALARM ALARM ALARM ALARM OK
알람 :       발생                                해제   ← 알람 2건
```

80~90% 구간은 **"현재 상태를 바꾸지 않는 완충 지대"** 다. 완충 지대가 넓을수록 안정적이지만, 해제가 늦다.

> 같은 원리가 어디에나 있다. 에어컨이 설정 온도에 딱 맞춰 켜졌다 꺼졌다 하지 않고 ±1도 간격을 두는 것, 비동기 로거가 "가득 참"을 `capacity/10` 이상 비어야 해제하는 것(P104)이 모두 히스테리시스다.

---

## 5. 해법 2 — 연속 N회 조건

한 번 튄 값(스파이크)에도 알람을 내면 잡음이 된다. **연속으로 N번 조건을 넘어야** 켠다.

```
N = 3, 임계 90
측정 :  95   70   95   96   97
카운트:  1    0    1    2    3    ← 세 번째 연속 초과에서 비로소 발생
```

| 방법 | 거르는 것 | 대가 |
|---|---|---|
| 히스테리시스 | 임계 근처의 **깜박임** | 해제가 늦다 |
| 연속 N회 | 순간적인 **스파이크** | 발생이 (N−1)회 검사 간격만큼 늦다 |

둘은 목적이 달라서 **함께** 쓴다. 해제 쪽에도 "연속 M회 정상"을 요구할 수 있다.

---

## 6. 등급이 여러 개일 때

경미(minor) / 주의(major) / 위험(critical) 같은 **임계 여러 개**를 둘 수 있다. 예: 80%, 90%, 100%.

```
사용률 :  75    85       95       100      70
등급   : 정상  minor    major    critical  정상
알람   :        발생(m)  등급상승 등급상승  해제
```

- 등급이 **올라가면** 새 알람(또는 등급 변경 알람)을 낸다. 악화는 새 정보다.
- 등급이 내려오면 "아직 알람 중이지만 완화됨"으로 알릴지, 모두 풀릴 때만 해제를 낼지 **정책**이다.
- 단계마다 히스테리시스를 따로 둘 수도 있다.

---

## 7. 감지 지연

대부분의 알람은 **감시자가 주기적으로 검사**해서 올린다.

```
검사 주기 3초
 0s ─── 3s ─── 6s ─── 9s
        ▲ 여기서 문제 발생(3.1s)        ▲ 다음 검사(6s)에서 처음 발견
```

문제가 생긴 순간부터 알람까지는 **최대 한 주기**, 연속 N회 조건을 쓰면 **최대 N주기**만큼 걸린다. 반대로 해제도 같은 만큼 늦다. 그래서 "문제는 이미 끝났는데 알람이 남아 있다", "문제 직후인데 알람이 안 뜬다"가 정상일 수 있다.

---

## 8. 알람 폭주를 막는 법

| 문제 | 방법 |
|---|---|
| 같은 조건이 계속 → 같은 알람 반복 | **상태가 바뀔 때만** 낸다 (§2) |
| 하나의 원인이 수십 개의 알람을 유발 (DB 가 죽자 그걸 쓰는 모든 서비스가 알람) | 원인 알람을 **상위**로, 파생 알람은 억제 |
| 임계 근처 깜박임 | 히스테리시스 (§4) |
| 알람 저장소가 가득 참 | 알람 이력 큐 자체도 **한도와 알람**이 필요하다 |

알람이 너무 많으면 사람은 **모두 무시**하기 시작한다. 알람은 "행동이 필요한 것"만 남기는 게 좋다.

---

## 9. 알람이 안 올 때

알람 시스템은 **감시자**(프로세스) → **대상**(무엇을 보나) → **임계**(언제 켜나) 순서다. 안 오면 같은 순서로 확인한다.

| 순서 | 확인 | 흔한 원인 |
|---|---|---|
| 1 | 감시자가 **살아 있나** | 감시 프로세스가 죽었다 (감시자를 감시하는 장치가 필요) |
| 2 | 대상이 **감시 목록에** 있나 | 설정에 등록되지 않았다 |
| 3 | 임계가 **너무 높지** 않나 / 검사 주기가 너무 길지 않나 | 지나치게 느슨한 기준 |
| 4 | 알람을 **전달하는 경로**가 살아 있나 | 알람 서버·큐 문제 |
| 5 | 해제 조건이 **충족됐는데 못 읽은** 건 아닌가 | 알람이 계속 떠 있는 이유 |

---

## 10. 정리

1. 알람은 **상태**이고, 발생과 해제가 **짝**이다. 상태가 바뀔 때만 낸다.
2. 임계 하나는 깜박인다 → **히스테리시스**(켜는 기준 ≠ 끄는 기준) + **연속 N회**.
3. 감지는 **주기 검사**라 한 주기 늦다. 지연은 버그가 아니라 설계다.
4. 안 올 때는 **감시자 → 대상 → 임계 → 경로** 순으로 찾는다.
