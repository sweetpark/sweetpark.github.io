## 1. 값의 종류

| 종류 | 예 | 성질 | 구간 값을 구하는 법 |
|---|---|---|---|
| **카운터(합계)** | 요청 건수, 에러 건수 | 계속 **증가**만 한다 | `이번 누적 − 지난 누적` |
| **게이지(현재값)** | 현재 접속자 수, 큐 길이, 메모리 사용량 | **오르내린다** | 읽은 시점의 값 / 구간 안의 최대·최소·평균 |
| **평균/최대/최소** | 평균 응답시간, 최대 큐 길이 | 구간마다 새로 계산 | 구간 안의 값들로 계산 |

종류를 헷갈리면 틀린 결과가 나온다. "현재 접속자 수"를 카운터처럼 누적하면 의미 없는 숫자가 된다.

## 2. 누적 카운터와 차분

가장 흔한 구조는 이렇다.

```
 서비스 프로세스                      수집기                    파일
 요청 1건 처리마다 counter += 1       1분마다 counter 를 읽는다     구간 값을 기록
 (공유메모리/변수에 누적)             ───────────────────────▶
                                      11:00 읽음 → 1000
                                      11:01 읽음 → 1063   → 이번 분 = 1063 − 1000 = 63
                                      11:02 읽음 → 1063   → 이번 분 = 0
```

이 구조의 장점:

| 장점 | 이유 |
|---|---|
| **세는 쪽이 가볍다** | 원자적 증가 한 번이면 끝. 구간 경계, 파일 쓰기를 몰라도 된다 |
| **읽는 쪽이 한 번 놓쳐도 괜찮다** | 누적값은 남아 있으니, 다음에 읽을 때 두 구간의 합이 한꺼번에 잡힌다 |
| **세는 쪽이 죽어도 값이 이어질 수 있다** | 누적값을 공유메모리에 두면 프로세스가 재시작해도 그대로다 |

한 번 놓친 경우:

```
11:00 읽음 → 1000
11:01 읽기 실패!
11:02 읽음 → 1130   → 두 분 합계 130 (분배는 못 하지만 총량은 정확)
```

## 3. 카운터가 되돌아갈 때

누적값이 줄어들면 `이번 − 지난` 이 **음수**가 된다. 원인:

| 원인 | 예 |
|---|---|
| 카운터를 가진 **프로세스 재시작** | 메모리에 있던 누적값이 0 으로 초기화 |
| **오버플로(wrap)** | 32비트 정수가 최대값을 넘어 0 부근으로 |
| 수동 초기화 | 운영자가 리셋 |

```
지난 값 1000, 이번 값 7   → 차이 −993 ???
```

보정 방법(가장 흔한 것): **음수면 "되돌아갔다"고 보고, 이번 값 자체를 이번 구간의 증가량으로 본다.**

```
지난 1000, 이번 7 → 재시작 후 7건 센 것으로 간주 → 이번 구간 = 7
```

완벽하진 않다(재시작 직전 구간의 일부는 잃는다). 그래서 **재시작이 있었다는 사실** 자체를 따로 알 수 있으면 좋다. 누적값을 공유메모리에 두면 재시작에도 값이 이어져 이 문제가 줄어든다.

---

## 4. 롤업 — 1분을 5분, 1시간으로

1분마다 모은 값을 5분, 1시간, 하루 단위로 합쳐 둔다. **종류별로 합치는 법이 다르다.**

| 종류 | 5분 값 = |
|---|---|
| 카운터(합계) | 5개 1분 값의 **합** |
| 최대 / 최소 | 5개의 **최대 / 최소** |
| 게이지(현재값) | **마지막** 분의 값 (또는 평균·최대) |
| **평균** | **건수로 가중한 평균** (아래) |

**평균의 평균은 틀린다.**

```
1분차: 평균 응답 10ms, 100건
2분차: 평균 응답 40ms, 900건

단순 평균   (10 + 40) / 2                 = 25ms   ← 틀림
가중 평균   (10×100 + 40×900) / (100+900) = 37ms   ← 맞음
```

1분차는 100건뿐이므로 영향이 작아야 한다. 그래서 평균 통계는 **합계와 건수를 같이** 저장해 두었다가 합칠 때 `총합계 ÷ 총건수`로 계산하는 것이 안전하다. (평균 자체만 저장하면 나중에 정확히 합칠 수 없다.)

---

## 5. 합계 검산

항목끼리 지켜야 하는 **불변식**이 있다면 매번 검산할 수 있다.

```
요청 수 = 성공 응답 수 + 타임아웃 수 + 취소 수
 63    =      48       +     15       +   0
```

63건 보내고 통계에 `REQ=63, RSP=48, TIMEOUT=15` 가 나오면 합이 맞다. 합이 안 맞으면:

| 불일치 | 의심 |
|---|---|
| 요청 > 성공+실패 | 아직 **진행 중**인 요청이 있거나, 어떤 종료 경로에서 카운트를 빠뜨림 |
| 요청 < 성공+실패 | **중복 카운트** (재진입 경로에서 요청을 또 셈) |
| 어떤 항목만 비정상으로 큼 | 그 항목의 타입·초기화·카운트 위치 |

---

## 6. 언제 보이나

수집은 **구간 경계에서만** 한다. 그래서 방금 한 일은 이렇게 보인다.

| 보는 곳 | 방금 한 일이 |
|---|---|
| 누적값을 직접 읽는 명령 (공유메모리) | **바로** 보인다 |
| 분 단위 통계 파일 | **다음 분 경계가 지난 뒤** 새 파일에 나온다 |
| 5분/1시간 통계 | 그 구간이 끝난 뒤 |

"통계 파일에 안 나온다"고 해서 바로 고장은 아니다. **경계가 지났는지** 먼저 확인한다.

---

## 7. 정리

1. 값은 **카운터 / 게이지 / 평균**으로 나누고, 종류에 맞게 합친다.
2. 세는 쪽은 **누적값만 올리고**, 구간 값은 읽는 쪽이 **차이**로 만든다. 가볍고 안전하다.
3. 누적값은 **되돌아갈 수 있다** — 음수 차이는 재시작·오버플로로 보고 보정한다.
4. 평균은 **건수 가중**, 게이지는 합치지 않는다. 마지막에 **합 불변식으로 검산**한다.
