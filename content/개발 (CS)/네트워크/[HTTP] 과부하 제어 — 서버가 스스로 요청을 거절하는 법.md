## 1. 왜 받아 주지 않는 게 더 낫나

식당을 떠올려 보자. 좌석이 40개인데 손님을 100명 입장시키면 어떻게 될까?

- 주방은 40명분만 만들 수 있다. 나머지 60명은 줄을 서서 **오래 기다린다.**
- 오래 기다린 손님은 **화가 나서 나가고**, 이미 만들어진 음식은 버려진다.
- 그 사이에도 새 손님이 계속 들어와, **끝내 아무도 제때 먹지 못한다.**

서버도 같다.

```
 처리 능력: 초당 1000건
 들어오는 요청: 초당 1200건
   → 대기 큐가 매초 200건씩 쌓인다
   → 대기 시간이 길어진다 (큐가 5초 분량이면 응답이 5초 늦다)
   → 클라이언트 타임아웃(예: 3초)이 먼저 만료된다
   → 서버는 이미 포기한 요청을 계속 처리한다 (헛수고)
   → 클라이언트는 재시도한다 → 요청이 더 늘어난다 → 악순환
```

그래서 정책은 하나다.

> **받을 수 있는 만큼만 받고, 나머지는 즉시 "지금은 안 됩니다"라고 돌려보낸다.**

이것을 **로드 셰딩(load shedding)** 이라 부른다. 거절한 요청은 실패지만, **받아 준 1000건은 제때 성공한다.** 전부 받았을 때 1200건이 전부 늦거나 실패하는 것보다 낫다.

> 거절은 **값싸야** 한다. 요청 본문을 다 읽고, 파싱하고, DB를 조회한 뒤에 거절하면 거절이 이미 비싸다. 가능한 한 **앞단(연결·헤더 단계)** 에서 막는다.

## 2. 거절을 알리는 방법

### 2-1. HTTP 응답 코드

| 코드 | 이름 | 의미 | 클라이언트가 할 일 |
|---|---|---|---|
| **429** | Too Many Requests | **당신이** 너무 많이 보낸다 (클라이언트별 속도 제한) | 보내는 속도를 줄인다 |
| **503** | Service Unavailable | **서버가** 지금 처리할 수 없다 (과부하·점검) | 잠시 후 다시 시도 |

`Retry-After` 헤더로 시점을 알려 줄 수 있다.

```
HTTP/1.1 503 Service Unavailable
Retry-After: 5          ← 5초 뒤에 다시 오라 (날짜 형식도 가능)
```

### 2-2. HTTP/2 에서는 연결 단위의 도구가 더 있다

| 도구 | 범위 | 뜻 |
|---|---|---|
| `SETTINGS_MAX_CONCURRENT_STREAMS` | 연결 | "한 연결에서 동시에 열 수 있는 스트림은 N개까지" |
| `RST_STREAM` + **`REFUSED_STREAM`**(0x7) | 스트림 하나 | "이 요청은 **처리를 시작하지 않았다.**" |
| `GOAWAY` | 연결 전체 | "이 연결에서 더 이상 새 요청을 받지 않겠다" |

`REFUSED_STREAM` 이 중요한 이유: 서버가 **아무것도 처리하지 않았음을 보장**하므로, 클라이언트는 **중복 처리 걱정 없이** 같은 요청을 다시 보내도 된다. 반대로 처리 도중에 끊긴 요청은 다시 보내면 두 번 처리될 수 있어 멱등성(같은 요청을 여러 번 해도 결과가 같은 성질)을 따져야 한다.

## 3. 무엇을 보고 거절하나

| 지표 | 보는 법 | 어울리는 병목 |
|---|---|---|
| **TPS** | 1초 같은 구간에 들어온 요청 수를 센다. 한도(예: 1000)를 넘는 요청은 거절 | 처리 시간이 비슷한 요청이 대부분일 때 |
| **CPU 사용률** | 주기적으로 읽는다 (예: 1초마다) | 계산이 병목일 때 |
| **메모리 사용률** | 같은 방식 | 요청마다 메모리를 잡을 때 |
| **큐 길이 / 지연** | 대기 중인 요청 수, 처리 대기 시간 | 가장 직접적인 신호 |
| **동시 연결 수 / 초당 신규 연결 수** | 연결 단위로 센다 | 재접속 폭풍, 연결 자체가 비쌀 때 |

**TPS 를 세는 가장 단순한 방법 — 고정 구간(fixed window):**

```
구간 = 1초, 한도 = 1000
 0.0~1.0초: 요청 1200건 도착 → 앞의 1000건 처리, 200건 거절
 1.0초에 카운터를 0으로 리셋 → 다시 1000건까지 받음
```

단점: 구간 경계에 몰리면 **0.9~1.1초 사이에 2000건**이 통과할 수 있다. 더 정교한 방식(슬라이딩 윈도우, 토큰 버킷)이 있지만, 고정 구간은 구현이 쉽고 앞단에서 값싸게 쓸 수 있다.

> 사용률 지표(CPU·메모리)는 **주기적으로 읽기** 때문에 반응이 늦다. 읽는 주기가 1초면 최대 1초 동안은 과부하를 모른 채 받아 준다. 그래서 TPS·큐 길이 같은 즉각적인 지표와 **같이** 쓰는 경우가 많다.

## 4. 단계별 거절

한 번에 "전부 받음 / 전부 거절"로 바꾸면 서비스가 뚝뚝 끊긴다. 보통 **단계**를 둔다.

| 단계 | 사용률 | 거절 비율(예) | 의미 |
|---|---|---|---|
| 정상 | 50% 미만 | 0% | 전부 처리 |
| 경미(minor) | 50~70% | 일부 | 덜 중요한 요청부터 거절 |
| 주의(major) | 70~90% | 많이 | |
| 위험(critical) | 90% 이상 | 대부분 | 핵심 요청만 통과 |

거절 비율을 두는 방식("사용률이 70%를 넘으면 요청 10건 중 N건을 거절")은 한계를 넘는 순간 절벽처럼 떨어지는 것을 막는다.

**풀 때는 여유를 둔다.** 사용률이 임계 90% 에 걸쳐 89 → 91 → 89 → 91 로 흔들리면, 거절 시작과 해제를 초당 수백 번 반복하게 된다. "90% 에서 시작, **80% 아래로 내려가야 해제**" 처럼 간격을 두는 것이 히스테리시스다. ([알람 상태 머신](개발%20%28CS%29/인프라/모니터링·네트워크/[모니터링]%20알람%20상태%20머신%20—%20임계·히스테리시스·발생과%20해제.md)에서 자세히)

## 5. 연결 단계에서 막기

요청이 오기 전에, **연결을 맺는 속도**부터 제한할 수 있다.

| 제한 | 막는 것 |
|---|---|
| 초당 신규 연결 수 (예: 100) | 재접속 폭풍, 연결 맺기 공격 |
| 상대(피어)당 최대 연결 / 최대 동시 스트림 | 한 상대가 자원을 독점 |
| 최대 피어 수 | 서버 전체 자원 보호 |

연결을 맺고 TLS 핸드셰이크까지 하고 나서 거절하면 이미 비용을 다 쓴 뒤다. **연결을 받기 전에(`accept` 이후 즉시 `close`, 또는 accept 속도 제한)** 거절하는 것이 가장 값싸다.

## 6. 클라이언트 쪽 규칙

서버가 아무리 잘 막아도, 클라이언트가 **모두 같은 순간에 재시도**하면 서버는 다시 쓰러진다.

| 규칙 | 설명 |
|---|---|
| `Retry-After` 를 **따른다** | 서버가 알려 준 시간 전에는 다시 보내지 않는다 |
| **지수 백오프** | 재시도 간격을 1초 → 2초 → 4초 → 8초… 로 늘린다 |
| **지터(jitter)** | 간격에 무작위를 섞는다. 1만 개 클라이언트가 같은 4초 뒤에 몰려오지 않도록 |
| **재시도 횟수 상한** | 무한 재시도는 서버가 살아나는 것도 막는다 |
| `REFUSED_STREAM` 은 **안전하게** 재시도, 처리 중 끊김은 **멱등성** 확인 | §2-2 |

## 7. 정리

1. 한계를 넘기 전에 **일부러 거절**하는 것이 모두를 살린다 (로드 셰딩).
2. 거절은 **앞단에서 값싸게**, 신호는 **구분해서** (429 / 503 / `REFUSED_STREAM`), 시점은 `Retry-After` 로.
3. 기준은 병목에 가까운 지표로, **단계**와 **풀 때의 여유**를 둔다.
4. 클라이언트는 **백오프 + 지터**로 재시도한다.
