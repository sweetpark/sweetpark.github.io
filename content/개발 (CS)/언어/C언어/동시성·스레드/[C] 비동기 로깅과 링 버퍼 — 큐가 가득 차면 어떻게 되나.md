# 비동기 로깅과 링 버퍼 — 큐가 가득 차면 어떻게 되나

## 📌 한눈에 보기 — 주의해야 할 점

로그를 **큐에 넣고 바로 돌아오게** 만들면 서비스가 느린 디스크에 끌려가지 않는다. 대신 *큐가 찬다*는 새로운 문제가 생긴다.

| # | 규칙 | 이유 | 상세 |
|---|---|---|---|
| 1 | 로그 호출은 **기다리지 않는다** | 로그 때문에 서비스가 멈추면 본말이 뒤집힌다 | [§1](#1-왜-비동기로-하나) |
| 2 | 큐가 차면 **정책을 먼저 정한다** — 기다림 / 버림 / 늘림 | 정하지 않으면 "어쩌다 그렇게 동작"한다 | [§3](#3-큐가-가득-차면--세-가지-정책) |
| 3 | 버리기로 했다면 **버린 개수를 센다** | 유실이 설계된 동작이어도 *얼마나 잃었는지*는 알아야 한다 | [§6](#6-유실을-알아채는-방법) |
| 4 | 종료할 때 **남은 로그를 다 쓰고** 끝낸다 | 장애 원인은 보통 *마지막 몇 줄*에 있다 | [§4](#4-로그가-사라지는-세-가지-길) |
| 5 | 프로세스가 **비정상 종료**하면 큐·버퍼에 있던 로그는 사라진다 | 그 메모리는 프로세스와 함께 없어진다 | [§4](#4-로그가-사라지는-세-가지-길) |
| 6 | "가득 참" 상태는 **여유를 두고 해제**한다 | 한 칸 비었다고 바로 풀면 상태가 계속 뒤집힌다 | [§5](#5-가득-참-상태에-여유를-두는-이유) |
| 7 | 소비자가 느려지는 **원인은 로거 밖**에 있다 | 디스크, 네트워크 파일시스템, 아무도 안 읽는 파이프… | [§7](#7-직접-해-보기) |

## 1. 왜 비동기로 하나

식당을 떠올려 보자. 홀 직원이 주문을 받고 **요리가 나올 때까지 주방 앞에서 기다린다면** 다른 손님은 받을 수 없다. 그래서 주문서를 **주문 걸이**에 걸어 두고 돌아간다. 주방(별도 스레드)은 걸이에서 하나씩 꺼내 요리한다.

동기 로깅은 직원이 기다리는 방식이다.

| | 동기 | 비동기 |
|---|---|---|
| `log()` 가 하는 일 | 파일에 **직접** 쓴다 | 큐에 **넣기만** 한다 |
| 디스크가 느려지면 | 서비스 스레드가 **같이 느려진다** | 서비스는 그대로, 큐만 **쌓인다** |
| 로그가 사라지는 경우 | 거의 없음 | 큐가 차거나, 큐를 비우기 전에 종료 |

```mermaid
flowchart LR
    S1["서비스 스레드 1"] --> Q["큐 (한정된 크기)"]
    S2["서비스 스레드 2"] --> Q
    Q --> W["쓰기 스레드"] --> F["파일 / 디스크"]
```

서비스 스레드는 큐에 넣고 바로 다음 일로 간다. **큐 → 파일** 구간만 느린 일을 맡는다.

## 2. 큐는 링 버퍼로 만든다

로그는 계속 들어오고 계속 나가므로, 크기가 고정된 배열을 **원형으로 돌려 쓰는** 링 버퍼가 알맞다. 넣을 때마다 `malloc` 하지 않아서 싸고, 최대 메모리 사용량도 처음부터 정해진다.

```c
/* 쓰기: 가득 차 있지 않으면 tail 칸에 넣는다 */
tail = (head + count) % cap;     /* head = 다음에 꺼낼 칸, count = 쌓인 개수 */
q[tail] = copy;
count++;
```

여러 스레드가 동시에 넣으므로 **뮤텍스**로 `head`·`count` 를 지키고, 쓰기 스레드는 큐가 비어 있는 동안 **조건변수**로 잔다(바쁜 대기로 CPU를 쓰지 않는다). 큐 자체는 [원형 큐 노트](개발%20%28CS%29/언어/C언어/동시성·스레드/[C]%20배열%20기반%20원형%20큐%28Ring%20Buffer%29%20—%20front·back%20인덱스로%20만드는%20큐.md)를 참고.

> [!NOTE] 호출자의 문자열은 **복사**해서 큐에 넣는다
> 포인터만 저장하면 호출자가 그 버퍼를 다른 내용으로 바꾸는 순간 로그 내용이 바뀐다.

## 3. 큐가 가득 차면 — 세 가지 정책

생산(서비스)이 소비(디스크)보다 빠르면 큐는 반드시 찬다. 이때 할 수 있는 일은 셋뿐이다.

| 정책 | 동작 | 장점 | 단점 | 어울리는 곳 |
|---|---|---|---|---|
| **기다림** (block) | 자리가 날 때까지 `log()` 가 기다린다 | 하나도 안 잃는다 | 서비스가 멈출 수 있다 (비동기의 의미가 사라진다) | 반드시 남겨야 하는 기록 (과금, 감사) |
| **버림** (drop) | 새 로그를 버리고 실패를 돌려준다 | 서비스는 절대 안 멈춘다 | 로그를 잃는다 | 일반 진단 로그 |
| **늘림** (grow) | 큐를 키운다 | 일단 안 잃는다 | 메모리가 끝없이 늘어 결국 프로세스가 죽는다 | 짧은 폭주 한정 (상한을 둘 것) |

일반 진단 로그는 대개 **버림**을 고른다. "로그가 서비스를 죽이는 일은 없어야 한다"는 판단이다.
**반드시 남겨야 하는 기록에는 비동기 로깅 큐를 쓰지 않는 것이 맞다.** 버려질 수 있기 때문이다.

> [!WARNING] 버림은 *조용히* 일어난다
> 호출자가 반환값을 확인하지 않으면 로그가 빠진 줄도 모른다. 그래서 다음 두 가지가 필요하다: 버린 개수를 세는 **통계**, 지금 가득 찬 상태인지 알려 주는 **상태 값**([§6](#6-유실을-알아채는-방법)).

## 4. 로그가 사라지는 세 가지 길

| # | 경로 | 언제 | 막는 법 |
|---|---|---|---|
| 1 | **가득 차서 버려짐** | 쓰기 스레드가 못 따라갈 때 (버림 정책) | 큐 크기·쓰기 속도 점검, 통계로 감지 |
| 2 | **종료 때 큐를 안 비움** | `destroy`/`flush` 없이 `exit()`·`_exit()` | 종료 절차에서 *큐가 빌 때까지 쓰고* 스레드를 join |
| 3 | **크래시 / `kill -9`** | 큐·버퍼가 있는 메모리가 프로세스와 함께 사라짐 | 막을 수 없다. 중요한 건 큐를 거치지 않거나, 크래시 시 기록을 따로 남긴다 |

두 가지를 구분해 두자.

- **`write()` 로 커널에 넘긴 것**은 프로세스가 `kill -9` 로 죽어도 파일에 남는다 (커널의 페이지 캐시에 있으므로). 전원이 꺼지면 그때는 `fsync` 를 안 한 것이 사라질 수 있다.
- **프로세스 안의 버퍼**(`stdio` 의 `printf`/`fwrite` 버퍼, 비동기 로거의 큐)에 있던 것은 프로세스가 갑자기 죽으면 사라진다.

그래서 동기 로깅(`write()` 직접 호출)은 `kill -9` 에서도 거의 다 남고, 비동기 로깅은 그 순간 큐에 있던 만큼 잃는다. 이것이 비동기의 대가다.

## 5. 가득 참 상태에 여유를 두는 이유

"가득 참"을 `count == cap` 일 때만 켜고 *한 칸이라도 비면 바로 끄면*, 소비와 생산이 비슷한 속도일 때 상태가 **초당 수천 번 켜졌다 꺼진다.** 이 상태 값으로 경보를 올리면 경보가 계속 울렸다 멈춘다.

에어컨이 목표 온도 *딱 한 지점*에서 켜졌다 꺼지면 계속 떨리는 것과 같다. 그래서 켜는 기준과 끄는 기준 사이에 **여유(히스테리시스)** 를 둔다.

| | 기준 |
|---|---|
| 켜기 | 큐가 가득 참 |
| 끄기 | 빈 칸이 `capacity / 10` 이상 (최소 1칸) |

## 6. 유실을 알아채는 방법

| 수단 | 내용 | 쓰임 |
|---|---|---|
| **통계** | 받은 줄 `enq`, 꺼낸 줄 `deq`, 버린 줄 `dropped`, 쌓인 줄 `used` | `enq − deq = used` 가 계속 커지면 소비가 못 따라가고 있다 |
| **상태 값** | `is_full()` | 지금 버리고 있는 중인지 |
| **반환값** | `log()` 가 `FULL` 을 돌려준다 | 호출자가 "이번 줄이 버려졌다"는 걸 안다 |
| **외부 감시** | 큐 사용률이 임계값을 넘으면 알람 | 사람이 로그를 보기 전에 알려 준다 |

버림 정책을 쓰는 로거가 **통계를 안 내놓으면** 유실을 알아낼 방법이 없다.

## 7. 직접 해 보기

### 느린 소비자를 흉내 내기 (순수 리눅스)

디스크가 느린 상황은 아무도 안 읽는 **파이프(FIFO)** 로 흉내 낼 수 있다. 파이프는 약 64KB가 차면 쓰는 쪽을 멈춰 세운다.

```bash
mkfifo /tmp/slow.log
sleep 300 < /tmp/slow.log &                 # 읽는 쪽을 열어 두되, 읽지는 않는다
yes | head -c 1000000 > /tmp/slow.log       # 64KB 쯤 쓰고 멈춘다 (Ctrl+C 로 중단)
```

이 파일을 로거의 출력 파일로 쓰면 *쓰기 스레드가 멈추고 → 큐가 차는* 상황이 그대로 재현된다.

### 코드로 연습

[P104 alog_ring](https://github.com/sweetpark/c-playgound/tree/main/drill/P104_alog_ring) — 한정 큐 + 소비 스레드를 직접 만든다.

| 시험이 확인하는 것 | 규칙 |
|---|---|
| 막힌 sink 에 100줄 연달아 쓰기 | 기다리지 않고 버린다, 받은 줄 + 버린 줄 = 100 |
| `destroy` 후 | 받은 줄이 **받은 순서대로 전부** 나간다 |
| FULL 해제 | 한 칸 비었다고 풀리지 않고, `cap/10` 칸이 비어야 풀린다 |
| 생산자 4명 동시에 | 하나도 잃지 않고 각자의 순서가 유지된다 |
