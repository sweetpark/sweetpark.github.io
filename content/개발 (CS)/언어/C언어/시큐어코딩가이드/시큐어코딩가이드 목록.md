# 시큐어코딩가이드 _index

> 「전자정부 SW 개발·운영자를 위한 C 시큐어코딩 가이드」(3판, 2012.9, 행정안전부·KISA) 기준
> **C 언어 기반 정보시스템의 보안약점 58개 — 원인·코드·대응**을 유형별 7개 Part로 정리한 시리즈.
> 58개를 암기하는 것이 목표가 아니다. **7개 유형의 사고 패턴**을 익혀, 새로운 코드를 봐도 어느 유형에 속하는지 판단할 수 있게 되는 것이 목표다.

---

## 학습 목표

1. 보안약점을 **"유형"** 으로 읽는다 — 58개가 아니라 7개 사고 패턴
2. C 특유의 위험 지점을 안다 — 포인터·경계·정수 타입·수동 자원관리
3. **Bad → Good 전환 패턴**을 손에 익힌다 — 코드 리뷰에서 즉시 지적할 수 있게
4. 우리 코드에 적용할 액션을 가져간다 — 금지 함수 목록, 릴리스 전 점검 항목, 정적분석 도입 방향

먼저 읽기: **[Part 0. 개요 — 신뢰경계와 C가 위험한 이유](개발%20%28CS%29/언어/C언어/시큐어코딩가이드/[시큐어코딩]%20Part%200.%20개요%20—%20신뢰경계와%20C가%20위험한%20이유.md)**. 58개 전부를 관통하는 질문 하나("이 데이터는 어디서 왔고, 나는 왜 믿고 있는가?")가 여기서 나온다.

## 각 항목의 표준 골격 (전 Part 공통)

```text
{번호}. {이름} `CWE-xxx`
  ├─ 신뢰 경계  : 외부 입력 ______ → 검증 없이 → 위험한 자리 ______
  ├─ ⚠️ 한줄 경고 (그대로 암기할 문장)
  ├─ 공격 시나리오
  ├─ ❌ Bad 코드
  ├─ ✅ Good 코드
  └─ 치환 규칙   : Bad → Good으로 바꾸는 동작 한 줄
```

각 계열 파일 끝에는 그 계열 전용 **미니 체크리스트**가 있다. 코드 리뷰할 때 그대로 대조한다.

## 체화 루틴 — 58개를 어떻게 내 것으로 만드는가

> [!TIP] 읽기만으로는 손에 안 붙는다 → [시큐어코딩 체화 드릴](개발%20%28CS%29/언어/C언어/실습/시큐어코딩%20체화%20드릴/README.md)
> 아래 3회차 반복은 "읽고 기억하기" 훈련이다. **실제로 Bad 코드를 타이핑해서 빌드하고, 취약점이 뚫리는 걸 눈으로 본 다음 Good으로 고쳐 쓰는** 손 훈련은 별도 드릴에서 한다 — 코드는 [GitHub repo](https://github.com/sweetpark/c-playgound)에서 직접 친다.

19개짜리 Part 1도 한 번에 안 외운다. **3회차 반복**으로 분산한다(각 Part 문서에도 동일하게 안내).

| 회차 | 보는 것 | 하는 일 |
| :--- | :--- | :--- |
| 1회차(읽기) | 계열/Part 파일 전체 | Bad/Good 코드를 나란히 읽고 **왜 다른지** 소리 내어 설명 |
| 2회차(가리기) | 항목 이름 + Bad 코드만 | Good 코드를 안 보고 직접 고쳐 쓴 뒤 비교 |
| 3회차(역방향) | ⚠️ 한줄 경고만 | 경고 문장만 보고 어떤 항목·어떤 Bad 코드였는지 떠올리기 |

- **금지 함수 스캐빈저 헌트**: 실제/예제 코드에서 [부록 위험함수 치환표](개발%20%28CS%29/언어/C언어/시큐어코딩가이드/[시큐어코딩]%20부록%20—%20위험함수%20치환표·암호화%20기준표·PQC%20전환.md)의 함수를 검색해 어느 Part·항목에 해당하는지 짝짓는다.
- **한 줄 경고 암송**: 58개의 ⚠️ 문장만 뽑아 카드로 순서를 섞어 반복한다 — 문장 하나가 CWE 하나와 방어책 하나를 동시에 압축하고 있다.
- **중간 점검 퀴즈**: [1-1 삽입 계열](개발%20%28CS%29/언어/C언어/시큐어코딩가이드/Part%201.%20입력데이터%20검증%20및%20표현/[시큐어코딩]%201-1.%20삽입%28Injection%29%20계열.md#중간-점검-스스로-답해보기), [2-2 자격증명 계열](개발%20%28CS%29/언어/C언어/시큐어코딩가이드/Part%202.%20보안기능/[시큐어코딩]%202-2.%20자격증명%20관리%20계열.md#중간-점검-인가와-자격증명) 안에 원문 그대로의 시나리오형 문제 6개가 있다.

## 코드 리뷰 · 릴리스 체크리스트

### 코드 작성·리뷰 시

- [ ] 외부 입력이 질의문·경로·명령·크기·인덱스로 흘러가는 경로를 그려봤는가
- [ ] 모든 배열 접근에 하한(0 이상)과 상한(MAX 미만) 검사가 있는가
- [ ] 복사 함수에 크기 인자가 있고, 복사 후 널 종료를 보장하는가
- [ ] 곱셈·덧셈·뺄셈 결과를 크기나 인덱스로 쓰기 전에 범위를 검사했는가
- [ ] signed 값이 unsigned 인자로 넘어가는 지점이 있는가
- [ ] 모든 반환값을 검사하고, 실패 시 동작이 코드에 적혀 있는가
- [ ] 자원 할당과 해제가 에러 경로를 포함한 모든 경로에서 짝을 이루는가
- [ ] 인증뿐 아니라 인가를 기능별로 다시 검사하는가

### 릴리스 직전

- [ ] 금지 함수(`gets`/`strcpy`/`sprintf`/`system`/`rand`)가 신규 코드에 없는가
- [ ] 소스와 주석에 패스워드·키·계정·내부 URL이 남아 있지 않은가
- [ ] 디버그 코드와 디버그 진입점이 릴리스 빌드에서 제외되었는가
- [ ] 오류 메시지에 경로·환경변수·스택 정보가 노출되지 않는가
- [ ] 생성되는 파일·디렉터리의 퍼미션이 최소 권한인가
- [ ] 컴파일 경고(`-Wall -Wextra -Wconversion`)가 0건인가
- [ ] 정적분석 결과의 High 등급이 모두 조치 또는 사유 기록되었는가
- [ ] 릴리스 바이너리에서 디버그 심볼이 제거(strip)되었는가

## 정적분석 도입 — 현실적으로 하는 법

1. **도구를 붙인다** — 컴파일러 경고부터: `-Wall -Wextra -Wconversion -Wsign-compare`. 여기에 무료 도구(cppcheck, clang-tidy, clang 정적분석기)를 추가.
2. **기준선(baseline)을 긋는다** — 기존 코드 전체를 지금 다 고치는 건 불가능. 현재 상태를 기준선으로 저장하고 "여기서 더 늘어나지 않게" 하는 것부터.
3. **신규·변경분만 막는다** — 가이드의 적용 범위(신규+유지보수 코드)와 동일. 새로 추가/수정된 코드에서 발생한 결함만 빌드 실패 처리. 저항이 가장 적고 효과는 즉시.
4. **오탐을 관리한다** — 억제(suppress)할 때는 반드시 사유를 코드 주석/관리 파일에 남기는 규칙.
5. **기준선을 조금씩 내린다** — 스프린트마다 기존 결함 N건씩 상환. High 등급부터, 우선순위(입력 검증 → 메모리 → 인가 → 자원) 순으로.
