# 메모리 정렬(Memory Alignment)과 aligned_alloc — CPU 워드 경계와 안전한 할당 래퍼

> [!NOTE]
> C11 표준의 `aligned_alloc`을 이용해 메모리 주소를 특정 바이트 단위(8/16/64바이트)의 배수로 정렬하는 이유와, 현대 CPU의 메모리 접근 원리, 그리고 표준 라이브러리 속성 키워드(`__wur`, `__attribute__`)를 활용한 실무형 안전 할당 래퍼(Wrapper) 패턴을 정리한다.

---

## 0. 왜 그냥 `malloc` 대신 메모리 정렬을 신경 쓰는가?

일반적으로 C에서 힙 메모리를 잡을 때는 `malloc(size)`을 쓴다. 하지만 고성능 서버, 네트워크 패킷 처리 엔진, 대용량 통신 데몬 등 극한의 속도와 안정성을 요구하는 시스템에서는 **메모리 시작 주소가 몇 번지인지(정렬 여부)**를 매우 엄격하게 통제한다.

그 이유는 소프트웨어 문법이 아니라 **컴퓨터 하드웨어(CPU)의 메모리 읽기/쓰기 방식**에 있다.

---

## 1. 하드웨어 관점: CPU는 메모리를 어떻게 읽는가?

현대 64비트 CPU는 메모리를 1바이트씩 낱개로 읽지 않는다. 데이터 버스(Data Bus) 폭에 맞춰 **8바이트(64비트, 1 Word)** 단위의 청크(Chunk)로 한 번에 퍼 올린다.

### 1.1 정렬(Aligned) 접근 vs 비정렬(Unaligned) 접근

주소가 **8의 배수(0x...0, 0x...8)**로 예쁘게 맞춰져 있는 경우와 홀수 주소에 걸친 경우의 차이를 비교해 보자:

```
[ Case 1: 8바이트 정렬된 메모리 (Aligned: 주소 0x1000) ]
0x1000 ~ 0x1007 (8바이트 데이터: uint64_t 또는 포인터)
┌───┬───┬───┬───┬───┬───┬───┬───┐
│ B0│ B1│ B2│ B3│ B4│ B5│ B6│ B7│
└───┴───┴───┴───┴───┴───┴───┴───┘
CPU 동작: 메모리 버스에서 0x1000~0x1007 블록을 딱 1번만 읽으면 끝! (단일 사이클)


[ Case 2: 정렬되지 않은 메모리 (Unaligned: 예: 주소 0x1003) ]
데이터가 0x1003 ~ 0x100A에 걸쳐 쪼개져 있는 경우:
[0x1000 ~ 0x1007 블록]              [0x1008 ~ 0x100F 블록]
┌───┬───┬───┬───┬───┬───┬───┬───┐   ┌───┬───┬───┬───┬───┬───┬───┬───┐
│   │   │   │ B0│ B1│ B2│ B3│ B4│   │ B5│ B6│ B7│   │   │   │   │   │
└───┴───┴───┴───┴───┴───┴───┴───┘   └───┴───┴───┴───┴───┴───┴───┴───┘
CPU 동작:
  1) 0x1000~0x1007 블록을 먼저 읽음 (1회 버스 사이클)
  2) 0x1008~0x100F 블록을 추가로 읽음 (2회 버스 사이클)
  3) CPU 레지스터 내부에서 비트 시프트와 마스킹 연산으로 8바이트를 합침
```

### 1.2 비정렬 접근의 2대 치명적 문제
1. **성능 저하 (Performance Penalty)**: 메모리 접근 횟수가 2배로 늘어나고 내부 조합 연산이 추가되어 메모리 처리량이 급격히 떨어진다.
2. **하드웨어 크래시 (Bus Error)**: x86 계열 CPU는 하드웨어 차원에서 비정렬 접근을 조용히 처리해주지만(속도만 느려짐), 일부 ARM 코어나 네트워크 가속 칩, 임베디드 RISC 프로세서에서는 비정렬 주소 역참조 시 즉시 **하드웨어 버스 에러(`SIGBUS`)**를 발생시키며 프로세스가 죽는다.

따라서 64비트 시스템의 고성능 자료구조는 **모든 힙 메모리 시작 주소를 8바이트(또는 캐시 라인 크기인 64바이트)의 배수로 강제 정렬**하는 것이 정석이다.

## 2. C11 `aligned_alloc` 표준 함수와 컴파일러 지시어 해독

C11 표준 이전에는 POSIX 전용 함수인 `posix_memalign()`이나 컴파일러 내장 함수를 썼지만, **C11(ISO C)**부터 표준 라이브러리(`<stdlib.h>`)에 `aligned_alloc()`이 공식 도입되었다.

### 2.1 표준 라이브러리 내부 선언문 해독
표준 헤더 파일을 열어보면 다음과 같은 선언문이 적혀 있다:

```c
#ifdef __USE_ISOC11
/* ISO C variant of aligned allocation.  */
extern void *aligned_alloc (size_t __alignment, size_t __size)
     __THROW __wur __attribute__ ((__malloc__, __alloc_size__ (2)));
#endif
```

| 키워드 / 속성 | 의미 및 역할 |
| :--- | :--- |
| **`__USE_ISOC11`** | 2011년 제정된 **C11 표준(ISO/IEC 9899:2011)** 모드에서만 활성화되는 표준 함수임을 의미 |
| **`__alignment`** | 메모리 시작 주소의 배수 (반드시 **2의 거듭제곱**: 8, 16, 32, 64 등) |
| **`__size`** | 할당할 총 바이트 크기 (C11 규격상 **`__size`는 `__alignment`의 배수**여야 함) |
| **`__THROW`** | C++ 컴파일러와 함께 쓰일 때 "이 함수는 예외(Exception)를 던지지 않는다(`noexcept`)"를 명시 |
| **`__wur`** | **W**arn **U**nused **R**esult. **"반환값을 변수에 받지 않고 버리면 컴파일 경고를 띄워라!"** (할당된 주소를 무시하면 100% 메모리 누수가 발생하므로 컴파일 단계에서 차단) |
| **`__attribute__ ((__malloc__))`** | "이 함수가 반환한 포인터는 기존의 다른 포인터와 메모리가 겹치지 않는다(No Aliasing)"는 힌트를 컴파일러에게 주어 최적화 유도 |
| **`__attribute__ ((__alloc_size__ (2)))`** | "이 함수의 **2번째 인자(`__size`)**가 할당된 버퍼의 크기다"라고 컴파일러 정적 분석기에 알려주어 버퍼 오버플로우를 사전에 감지 |

## 3. 실무형 안전 메모리 할당 래퍼(Wrapper) 설계 패턴

실무 프로젝트에서는 개발자가 소스 코드 전역에서 원시 `malloc()`을 직접 호출하도록 두지 않는다. 
직접 호출하게 두면:
1. 주소 정렬이 보장되지 않고,
2. 실패 시 에러 로깅을 빼먹기 쉽고,
3. **`malloc`은 메모리를 0으로 초기화하지 않아 쓰레기값(와일드 포인터) 버그**를 유발하기 때문이다.

이를 방지하기 위해 프로젝트 공통 유틸리티로 **"3대 안전장치를 내장한 메모리 할당 래퍼"**를 구현하여 사용한다.

```c
#define MEM_ALIGN_8     8   /* 64비트 시스템 기본 8바이트 정렬 */

/**
 * @brief 8바이트 정렬 및 0 초기화가 보장되는 안전한 메모리 할당 래퍼
 * @param ul_mem_size 할당할 바이트 크기
 * @return void* 할당된 힙 메모리 포인터 (실패 시 NULL)
 */
void *safe_malloc(unsigned long ul_mem_size)
{
    void *pv_mem = NULL;
    char sz_error[128] = "";

    // 1. 8바이트 정렬된 메모리 할당 (CPU 접근 성능 최적화)
    pv_mem = aligned_alloc(MEM_ALIGN_8, ul_mem_size);
    
    // 2. 메모리 부족(OOM) 등으로 실패 시 시스템 에러 로그 기록
    if (pv_mem == NULL) {
        strerror_r(errno, sz_error, sizeof(sz_error));
        LOG_ERR("aligned_alloc(%d, %lu) failed, errno(%d:%s) (%s/%d)\n", 
                MEM_ALIGN_8, ul_mem_size, errno, sz_error, __func__, __LINE__);
        return NULL;
    }

    // 3. ★ 할당받은 메모리를 0으로 즉시 초기화 (calloc 효과)
    //    구조체 내부의 포인터는 NULL, 카운터는 0으로 자동 리셋되어 쓰레기값 버그 차단
    memset(pv_mem, 0x00, ul_mem_size);

    return pv_mem;
}
```

### 💡 래퍼 함수의 3가지 실무적 이점
1. **Zeroing 보장**: `memset(0x00)`을 강제하므로, 새로 할당받은 구조체의 모든 필드가 자동으로 `0`과 `NULL`이 된다.
2. **장애 추적 용이**: 메모리 고갈(`ENOMEM`)로 `malloc`이 실패했을 때 어느 소스의 몇 번째 줄에서 실패했는지 시스템 로그에 즉시 남는다.
3. **일관된 정렬**: 모든 개발자가 작성한 구조체 힙 메모리가 항상 8바이트 경계에 놓이므로 최상의 CPU 읽기 성능이 보장된다.

## 4. `malloc` vs `calloc` vs `aligned_alloc` 비교표

| 함수 | 정렬 보장 | 0 초기화 여부 | 실패 시 동작 | 주요 용도 |
| :--- | :---: | :---: | :---: | :--- |
| **`malloc(size)`** | 시스템 기본 (대개 8~16) | **X (쓰레기값 남음)** | `NULL` 반환 | 일반적인 메모리 할당 |
| **`calloc(n, size)`** | 시스템 기본 | **O (0으로 채움)** | `NULL` 반환 | 초기화가 필요한 배열 할당 |
| **`aligned_alloc(align, size)`** | **지정한 배수 완벽 보장** | X (쓰레기값 남음) | `NULL` 반환 | **하드웨어 버스/캐시라인 최적화, SIMD/AVX 연산** |
| **실무 안전 래퍼** | **지정한 배수 보장** | **O (자동 0 초기화)** | **시스템 에러 로깅** | **엔터프라이즈 서버/통신 데몬 공통 함수** |

---

## 5. 주의사항 (실무 함정)

1. **`alignment`는 반드시 2의 거듭제곱이어야 함**:
   - `aligned_alloc(12, 100)`처럼 2의 거듭제곱($2^n$)이 아닌 값을 주면 함수는 실패하고 `EINVAL` 에러를 뱉는다. 반드시 `8`, `16`, `32`, `64` 등을 사용해야 한다.
2. **`size`는 `alignment`의 배수여야 함**:
   - C11 표준에 따르면 두 번째 인자 `size`는 첫 번째 인자 `alignment`의 정수 배수여야 한다. 일부 OS/glibc는 배수가 아니어도 묵인하지만, 엄격한 환경에서는 `EINVAL`을 반환하므로 필요 시 `((size + align - 1) / align) * align` 공식으로 올림 처리(Padding)하여 넘겨주는 것이 이식성에 좋다.
3. **해제는 일반 `free()`를 사용**:
   - `aligned_alloc()`으로 할당받은 메모리도 해제할 때는 별도의 특수 함수 없이 **일반 `free(pv_mem)`**를 호출하면 된다.
