# 정수를 void 포인터 인자에 실어 보내기 — intptr_t 캐스팅 관용구

> [!NOTE]
> `pthread_create`처럼 인자를 딱 하나(`void *`)만 받는 함수에 정수 하나를 전달해야 할 때, `malloc` 없이 포인터 자체에 값을 실어 보내는 캐스팅 관용구와 그 이식성 문제를 정리한다.

## 0. 왜 필요한가

스레드를 여러 개 만들면서 각 스레드에 서로 다른 정수 하나(파일 디스크립터, 인덱스 번호 등)만 넘기고 싶은 상황을 생각해보자. `pthread_create`의 콜백은 인자를 `void *` 하나로만 받는다.

```c
void *worker(void *arg)
{
    int fd = *(int *)arg;   /* 포인터가 가리키는 곳에서 값을 읽어온다 */
    /* ... */
    return NULL;
}

int fd = 5;
pthread_create(&tid, NULL, worker, &fd);   /* fd의 "주소"를 넘긴다 */
```

값 하나 넘기자고 `&fd`처럼 지역 변수의 주소를 넘기면, `fd`가 스레드 시작 전에 스코프를 벗어나거나 값이 바뀌어버릴 위험이 있다([실무 C 코드 관례와 UB 함정 정리]([C]%20실무%20C%20코드%20관례와%20UB%20함정%20정리.md)의 B3와 같은 종류의 문제). 매번 `malloc`해서 안전하게 넘기는 게 정석이지만, 정수 하나 넘기자고 힙 할당과 해제를 짝지어 관리하는 것도 번거롭다.

## 1. 포인터 "안에" 값을 직접 욱여넣기

포인터는 결국 특정 크기(대개 64비트 시스템에서 8바이트)의 정수 값을 담는 그릇이다. 그 그릇에 **주소가 아니라 원하는 정수 값 자체**를 채워 넣고, 받는 쪽에서 그대로 정수로 꺼내 쓰면 별도의 메모리 할당 없이 값 하나를 전달할 수 있다.

```c
#include <stdint.h>   /* intptr_t */

int fd = 5;
pthread_create(&tid, NULL, worker, (void *)(intptr_t)fd);

void *worker(void *arg)
{
    int fd = (int)(intptr_t)arg;   /* 넣을 때와 반대 순서로 다시 꺼낸다 */
    /* ... */
    return NULL;
}
```

`arg`는 이제 진짜 메모리를 가리키는 주소가 아니다 — **값 그 자체가 포인터 변수 자리에 실려 있을 뿐**이므로, 절대 `*arg`처럼 역참조하면 안 된다.

## 2. 왜 `(void *)fd`로 바로 캐스팅하면 안 되는가

```c
void *arg = (void *)fd;   /* 컴파일러 경고: 정수를 포인터로 변환하는데 크기가 안 맞을 수 있음 */
```

`int`(대개 4바이트)를 포인터(64비트 시스템에서 8바이트)로 직접 캐스팅하면, 컴파일러 입장에서는 "크기가 다른 정수를 포인터에 억지로 끼워 넣는다"고 보고 경고를 낸다. 이 변환이 안전하다는 걸 보장하려면 **포인터와 정확히 같은 크기를 갖도록 표준이 보장하는 정수 타입**을 거쳐야 한다.

## 3. `intptr_t`/`uintptr_t`를 거쳐야 하는 이유 — 이식성

| 캐스팅 경로 | 문제 |
| --- | --- |
| `(void *)(int)fd` | `int`가 포인터보다 작은 플랫폼(대부분의 64비트 시스템)에서 값 손실 위험, 컴파일러 경고 |
| `(void *)(long)fd` | 대부분의 유닉스 계열에서 `long`이 포인터와 같은 크기라 실무에서 흔히 쓰이지만, **표준이 보장하는 것은 아니다**(플랫폼에 따라 `long`이 포인터보다 작을 수 있음) |
| `(void *)(intptr_t)fd` | `<stdint.h>`가 "포인터를 정수로 왕복 변환해도 정보 손실이 없다"고 **표준으로 보장**하는 전용 타입. 가장 안전한 선택 |

`long`을 거치는 방식이 리눅스/유닉스 계열 실무 코드에 여전히 흔한 이유는 그 플랫폼들에서는 실제로 `long`과 포인터 크기가 같기 때문이지만, 새로 짜는 코드라면 이런 용도로 정확히 만들어진 `intptr_t`(부호 있는 값용)/`uintptr_t`(부호 없는 값용)를 쓰는 게 표준적이고 이식성도 보장된다.

## 4. 이 관용구가 적합한 경우 vs 아닌 경우

- **적합**: 정수, 열거형, 상태 코드처럼 **값 하나**만 전달하면 되는 경우. 힙 할당/해제 관리 없이 값을 그대로 실어 보낼 수 있어 코드가 단순해진다.
- **부적합**: 필드가 두 개 이상인 구조체를 전달해야 하는 경우. "값 하나를 포인터 크기 안에 욱여넣는다"는 전제 자체가 깨지므로, 이때는 정직하게 구조체를 `malloc`하고 그 포인터를 넘겨야 한다(호출받는 쪽에서 다 쓴 뒤 `free`할지, 호출한 쪽이 계속 소유할지를 명확히 정해야 한다).

## 5. 자주 하는 실수

- **캐스팅 순서를 반대로 하기** — 값을 넣을 때는 `(void *)(intptr_t)fd`(정수 → 포인터 크기 정수 → 포인터), 꺼낼 때는 `(int)(intptr_t)arg`(포인터 → 포인터 크기 정수 → 원래 정수)로 방향이 대칭이다. 중간 타입(`intptr_t`)을 건너뛰고 바로 캐스팅하면 컴파일러 경고가 나거나, 경고를 무시하도록 강제 캐스팅해버려 이식성 문제를 감추게 된다.
- **`arg`를 실수로 역참조하기** — 이 값은 주소가 아니라 값 자체이므로 `*(int *)arg`처럼 포인터인 것처럼 역참조하면 존재하지도 않는 메모리 주소에 접근해 크래시가 난다. "값을 실어 보낸 포인터"와 "진짜 메모리를 가리키는 포인터"를 코드만 보고 구분하기 어려우므로, 이 패턴을 쓸 때는 변수명이나 주석으로 반드시 구분을 남겨야 한다.
- **부호 있는/없는 타입을 섞어 쓰다 부호 확장 문제 만들기** — 음수가 될 수 있는 값을 `uintptr_t` 경로로 보내거나, 반대로 큰 양수를 `intptr_t`로 다루면 값이 왜곡될 수 있다. 값의 부호 여부에 맞는 타입을 일관되게 고른다.
- **여러 스레드가 같은 값을 계속 재사용하는 반복문에서 이 패턴을 쓰다가 값이 예상과 다르게 캡처되는 문제** — 반복문 변수 자체를 매번 캐스팅해서 넘기면 값 자체는 그 순간 복사되므로 안전하지만, 만약 실수로 반복문 변수의 "주소"를 넘기는 방식과 섞어 쓰면(1번 항목의 `&fd` 방식과 혼용) 모든 스레드가 같은 최종 값을 보게 되는 흔한 버그로 이어진다.
