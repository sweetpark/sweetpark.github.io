## 📌 한눈에 보기

| 항목 | 내용 |
|---|---|
| 상황 | 같은 락을 쓰고 있는데도 느리거나(너무 넓음), 값이 어긋난다(너무 좁음) |
| 치환 규칙 | 락 안에는 **일관성이 필요한 공유 변수 접근만**, 느린 일은 락 밖으로 / **한 묶음인 연산**은 하나의 락 구간으로 |
| 장애 예 | 파일 쓰기 동안 모든 요청이 멈춘다 / `set` → `sum` → `prod` 사이에 남이 끼어들어 합과 곱이 서로 다른 입력 기준 |
| 원인 | 락의 시작과 끝을 "함수 경계"로 정했다 |
| 실습 문제 | [P121](https://github.com/sweetpark/c-playgound/tree/main/drill/P121_lock_scope) |

## 1. 이론 요약

```
너무 넓음                             너무 좁음
lock                                  lock; set(a,b); unlock          ← 스레드 A
  seq++                               ........  (스레드 B 가 set 으로 끼어든다)
  write(fd, ...)   ← 300ms             lock; s = a + b; unlock         ← A 의 합이 B 의 값 기준
unlock                                lock; p = a * b; unlock

고침:  lock; seq++; unlock;           고침:  lock; set; s = a+b; p = a*b; unlock;
       write(fd, ...)  ← 락 밖
```

| 항목 | 규칙 |
| :--- | :--- |
| 락 안에 둘 것 | 공유 변수 읽기·쓰기, 짧은 계산 |
| 락 밖으로 뺄 것 | 파일·네트워크 I/O, `sleep`, 사용자 콜백, 다른 락을 기다릴 수 있는 호출 |
| 줄일 것 | **느린 일**이지 공유 변수 접근이 아니다 (`++seq` 까지 빼면 번호가 겹친다) |
| 한 묶음 | `set → sum → prod`, `read → modify → write` 는 **하나의 락 구간** |
| 재귀 아님 | 락을 쥔 채 락을 잡는 함수를 부르면 `EDEADLK`(ERRORCHECK) 또는 교착. 안쪽은 락 없는 코드로 풀어쓰거나 `_locked` 버전을 둔다 |
| 읽기도 한 구간 | `get_a()`, `get_b()` 를 따로 부르면 서로 다른 시점의 값이 섞인다 → `snapshot` |

```diff
- lock; n = ++seq; io(n); unlock;                    /* I/O 가 락 안: 모두 줄을 선다 */
+ lock; n = ++seq; unlock; io(n);
- poly_set(p, a, b); s = poly_sum(p); q = poly_prod(p);      /* 함수 하나하나는 스레드 안전, 조합은 아니다 */
+ poly_op(p, a, b, &s, &q);                                  /* 한 락 구간 */
```

## 2. 재현 — 어디서 뚫리나

| 상황 | 틀린 코드의 결과 | 이유 |
|---|---|---|
| `io` 를 락 안에서 | `store_seq` 가 300ms 를 기다림 / 두 `io` 가 줄을 서서 600ms | 시험 `[A2]` 가 대기 시간과 io 동시 진행(`g_max_io == 2`)을 잰다 |
| `++seq` 를 락 밖으로 | 번호가 겹친다 (5만×4 번 호출에서 정확히 1..20만 이 한 번씩이어야) | 줄여야 할 것은 I/O 다 |
| `poly_op` 를 set/sum/prod 로 쪼갬 | 내 `(a,b)` 가 아닌 값의 합·곱 | 사이에 다른 스레드의 `set` |
| `snapshot` 을 getter 두 개로 | 존재한 적 없는 `(1, 20)` 상태를 읽음 | 시험 `[B3]` 가 `b == 2a` 를 확인 |
| `poly_op` 안에서 `poly_sum()` 호출 | `EDEADLK` 또는 교착 | 이미 쥔 락을 또 잡는다 |

## 3. 주의해야 할 점

1. **함수 하나하나가 스레드 안전해도 그 조합은 아니다**
	- `get_sum()` 도 안전하고 `get_product()` 도 안전하다. 둘을 이어서 부르는 코드는 안전하지 않다. 한 묶음은 **API 로** 제공하거나 호출하는 쪽에서 `_locked` 버전으로 묶는다
1. **락 범위를 넓힐수록 안쪽 함수의 락을 빼야 한다**
	- 재귀 락(`RECURSIVE`)으로 때우면 "락을 쥐고 불리나"가 코드에서 안 보이고 범위가 계속 넓어진다
1. **락 안에서 콜백을 부르지 않는다**
	- 콜백이 같은 락을 다시 잡으면 교착이다. 필요한 값은 락 안에서 복사해 두고 락 밖에서 콜백
1. **결정 기준**: "이 값들이 **한 번에 일관**되어야 하나?" — 그렇다면 한 구간, 아니면 분리

## 4. 변형 (부록)

### 변형 B — 락 안에서 `malloc`

- `malloc` 도 느릴 수 있다(내부 락, 메모리 부족 시 시스템 콜). 락 밖에서 할당하고 락 안에서는 포인터만 연결한다

### 변형 C — 락 안에서 `printf`

- `printf` 는 내부 락이 있고 터미널이 느리면 오래 걸린다. 로그는 락 안에서 문자열만 만들거나 비동기 로거([P104](https://github.com/sweetpark/c-playgound/tree/main/drill/P104_alog_ring))로
