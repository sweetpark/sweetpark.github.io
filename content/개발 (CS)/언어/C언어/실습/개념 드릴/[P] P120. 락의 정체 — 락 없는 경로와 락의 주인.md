## 📌 한눈에 보기

| 항목 | 내용 |
|---|---|
| 상황 | 한 스레드가 락을 쥐고 임계영역 한가운데(`a=70, b=0`)에 있다. 다른 스레드들은? |
| 치환 규칙 | 필드를 만지는 **모든 경로**가 같은 락을 잡는다 / 락은 **잡은 스레드만** 푼다 (`ERRORCHECK`) |
| 장애 예 | 읽는 쪽에 락이 없어서 합이 99 가 보인다. 다른 스레드가 `unlock` 해서 영역이 사라진다 |
| 원인 | 뮤텍스는 변수에 붙어 있지 않다. **약속**이다 |
| 실습 문제 | [P120](https://github.com/sweetpark/c-playgound/tree/main/drill/P120_lock_bypass) |

## 1. 이론 요약

```
스레드 A (락 보유)                    스레드 B (락 없이 읽기)        스레드 C (락 요구)
 lock                                                              box_sum()  ──▶ 대기 (영역 밖)
 a -= 30        a=70, b=0   ◀────────  x.a + x.b == 70 ✗ (깨진 값)     box_try_sum() ──▶ -EBUSY
 ...(멈춤)                                                          box_unlock() ──▶ -EPERM (내 락이 아님)
 b += 30        a=70, b=30
 unlock                                                            ──▶ 깨어나 100 을 읽는다
```

| 항목 | 규칙 |
| :--- | :--- |
| 락 없는 경로 | 락은 메모리를 막지 못한다. **락을 안 잡는 코드**는 임계영역 안에서 일어나는 일을 그대로 본다 |
| 락의 주인 | 잡은 스레드만 풀 수 있다. 남이 풀면 주인은 자기가 영역 안에 있다고 믿는데 락은 풀려 있다 |
| `ERRORCHECK` | 남의 락 풀기 → `EPERM`, 이중 잠금 → `EDEADLK` 로 알려 준다. `NORMAL` 은 조용히 통과하거나 교착 |
| `trylock` | 기다리지 않고 묻는다. 쥐고 있으면 `EBUSY` (내가 쥔 락이어도). **성공하면 락을 잡은 것**이라 확인만 하려던 코드가 락을 쥔 채 나갈 수 있다 |
| 반환값 | `pthread_mutex_*` 는 `errno` 가 아니라 **반환값(양수)**으로 에러를 준다. `< 0` 검사는 영원히 안 걸린다 |

```diff
- long box_sum(box_t *x) { return x->a + x->b; }                       /* 쓰는 쪽만 락 */
+ long box_sum(box_t *x) { lock; s = x->a + x->b; unlock; return s; }  /* 읽는 쪽도 같은 락 */
- pthread_mutex_init(&m, NULL);                                         /* NORMAL: 실수를 알려 주지 않는다 */
+ pthread_mutexattr_settype(&at, PTHREAD_MUTEX_ERRORCHECK);
```

## 2. 재현 — 어디서 뚫리나

| 상황 | 틀린 코드의 결과 | 이유 |
|---|---|---|
| 읽는 함수에 락이 없음 | 합이 99, 101 로 보인다 (시험 `[4]` 가 3만 번 확인) | 쓰는 도중의 중간 상태를 읽는다 |
| 새로 추가한 함수 하나가 락을 빼먹음 | 그 함수만 영역 밖에서 돈다 | 락은 협조 규칙이다 |
| 다른 스레드가 `unlock` | (NORMAL) 조용히 풀린다 → 주인은 계속 영역 안, 락은 열려 있다 | 주인 검사가 없다 |
| 같은 스레드가 두 번 `lock` | (NORMAL) 교착 | `ERRORCHECK` 라면 `EDEADLK` |
| `return -ERANGE` 앞에서 `unlock` 누락 | 다음 호출이 영원히 멈춤 | 실패 경로를 안 챙김 |
| `hook`(콜백)을 락 밖에서 호출 | 시험 `[3]` 에서 `try_sum` 이 `EBUSY` 가 아니라 성공 | 락 구간이 둘로 쪼개졌다 |

## 3. 주의해야 할 점

1. **"이 변수를 만지는 모든 곳"을 grep 한다**
	- 새 기능을 추가할 때 가장 많이 생기는 결함이다. 락 보호 대상은 변수이고, 락은 그 변수를 만지는 코드의 약속이다
1. **락 없는 읽기를 "성능" 때문에 허용하지 않는다**
	- 정말 락 없이 읽어야 한다면 원자 변수로 바꾼다 (락 없는 카운터). 단 여러 필드의 일관성은 원자 변수로 풀리지 않는다
1. **개발 빌드는 `ERRORCHECK`, 출시 빌드만 `NORMAL`** (또는 매크로로 전환)
1. **프로세스 사이로 확장하면** 락의 주인이 죽을 수 있다 → [P113](개발%20%28CS%29/언어/C언어/실습/개념%20드릴/[P]%20P113.%20공유메모리%20락%20—%20락을%20쥔%20채%20죽은%20프로세스%20복구하기.md)

## 4. 변형 (부록)

### 변형 B — `RECURSIVE` 뮤텍스

- 같은 스레드의 재잠금을 허용한다. 편하지만 "락을 쥐고 불리는가"가 코드에서 안 보이게 된다 → P121

### 변형 C — 스핀락과 비교

- 스핀락도 주인 개념이 없다(`pthread_spin_unlock` 은 누가 풀어도 된다). 언제 뮤텍스 대신 쓰나?
