# P115. 파이프 프레이밍 — 바이트 스트림에 메시지 경계 만들기

> [!TIP]
> - 이론: [IPC와 스레드 메모리 공유 비교](개발%20%28CS%29/CS%20기초/운영체제/[OS]%20IPC와%20스레드%20메모리%20공유%20비교.md), [POSIX IPC와 System V IPC 비교](개발%20%28CS%29/CS%20기초/운영체제/[OS]%20POSIX%20IPC와%20System%20V%20IPC%20비교%20—%20메시지%20큐%20중심.md)
> - 실습: [P115_pipe_frame](https://github.com/sweetpark/c-playgound/tree/main/drill/P115_pipe_frame) — `make P115` 로 채점
> - **P035 `write_all` 의 확장 문제**: P035 는 "한 번의 `write` 를 끝까지 쓰기"(부분 쓰기·EINTR·EAGAIN). 이 문제는 그 위에 **읽기 쪽(`read_exact`)·메시지 경계(프레이밍)·`PIPE_BUF` 원자성·`SIGPIPE`** 를 쌓는다
> - 대조: [P105 메시지 큐](개발%20%28CS%29/CS%20기초/운영체제/[OS]%20메시지%20큐가%20가득%20차면%20—%20용량·EAGAIN·블로킹,%20그리고%20죽은%20수신자.md)는 `send` 한 번 = `recv` 한 번(경계 있음). 파이프는 **경계가 없다**

## 📌 한눈에 보기

| 항목 | 내용 |
|---|---|
| 상황 | 두 프로세스가 파이프로 메시지를 주고받는다 |
| 치환 규칙 | `write`/`read` 를 **끝까지** 반복하는 도우미 + `[4바이트 길이][내용]` 프레이밍 |
| 장애 예 | `read(fd, buf, 100)` 이 40바이트만 돌려줬는데 100바이트로 처리 → 메시지가 쓰레기가 된다. 로컬 테스트에서는 우연히 맞아서 운영에서 터진다 |
| 원인 | 파이프·소켓은 몇 바이트가 오든 이상하지 않은 **바이트 스트림**이다 |
| 실습 문제 | [P115](https://github.com/sweetpark/c-playgound/tree/main/drill/P115_pipe_frame) |

## 1. 이론 요약

```
write(100) write(100)           read(150)  read(50)            ← 쪼개져 읽힐 수 있다
 ───────────────────▶ [ 200 바이트가 흘러가는 관 ] ───────────▶
                                                  read(500) → 200   ← 합쳐져 읽힐 수도 있다
```

| 항목 | 규칙 |
| :--- | :--- |
| 부분 쓰기 | `write` 가 `n` 보다 적게 돌려주면 **남은 만큼 이어서** 쓴다 (`O_NONBLOCK`, 시그널) |
| `EINTR` | 다시 시도한다 |
| `EAGAIN` | `poll` 로 기다렸다가 다시 한다 (`continue` 만 반복하면 CPU 100%) |
| EOF | `read` 가 0. **첫 바이트 전**이면 깨끗한 종료, **중간**이면 잘린 것 (`-ECONNRESET`) |
| 프레이밍 | `[길이 4바이트(빅엔디언)][내용]`. 길이는 **남이 쓴 값**이라 0, 최대치 초과를 거절 |
| 작은 버퍼 | 스트림은 되감을 수 없으니 **읽어서 버리고** `-EMSGSIZE` (메시지 큐의 "남는다"와 반대) |
| 원자성 | `PIPE_BUF`(4096) 이하의 `write` **한 번**만 원자적. 길이 칸+내용을 한 번에 |
| `SIGPIPE` | 읽는 쪽이 없으면 기본은 프로세스 즉사. 무시하고 `EPIPE` 로 받는다 |

```diff
- n = read(fd, buf, 100);  process(buf, 100);              /* 몇 바이트가 왔든 100 으로 처리 */
- write(fd, hdr, 4); write(fd, body, len);                 /* 두 번 → 쓰는 프로세스가 둘이면 끼어든다 */
+ if (pf_read_exact(fd, buf, 100) == 100) process(buf, 100);
+ memcpy(tmp, hdr, 4); memcpy(tmp + 4, body, len); pf_write_all(fd, tmp, 4 + len);   /* 한 번 */
```

## 2. 재현 — 어디서 뚫리나

| 상황 | 틀린 코드의 결과 | 이유 |
|---|---|---|
| 1MB 를 `O_NONBLOCK` 파이프에 쓴다 | 일부만 쓰이고 나머지는 **조용히 사라진다** | `write` 반환값을 안 봤다 |
| 시그널이 날아오는 프로그램 | 가끔 "연결이 끊겼다" | `EINTR` 을 에러로 처리했다 |
| 쓰는 프로세스 4개가 같은 파이프에 | 프레임이 어긋나 이후 전부 쓰레기 | 길이 칸과 내용을 `write` 두 번으로 나눴다 |
| 길이 칸이 `0xFFFFFFFF` | 4GB 를 읽거나 할당하려 든다 | 남이 쓴 길이를 믿었다 (시큐어코딩 SD51 "무한 자원 할당") |
| 버퍼가 작아 읽지 않고 돌아감 | 다음 호출이 내용 한가운데를 길이 칸으로 읽음 | 스트림은 되감을 수 없다 |
| 읽는 쪽이 먼저 죽음 | 쓰는 쪽 데몬 전체가 즉사 | `SIGPIPE` 를 무시하지 않았다 |

## 3. 주의해야 할 점

1. **로컬에서 되는 코드가 운영에서 터진다**
	- 같은 머신, 작은 메시지, 한 프로세스가 쓰고 한 프로세스가 읽으면 한 번에 다 읽히는 일이 많다
	- 지연·부하·큰 메시지에서 쪼개지기 시작한다. 시험이 일부러 느린 읽기와 시그널 폭풍을 만든다
1. **"원자적"은 `PIPE_BUF` 이하의 `write` 한 번에만 해당한다**
	- 그 이상은 다른 쓰는 프로세스의 데이터가 사이에 끼어들 수 있다
	- 큰 메시지는 쓰는 프로세스를 하나로 제한한다
1. **블로킹 read/write 도 `EINTR` 이 난다**
	- `SA_RESTART` 없이 시그널 핸들러가 있으면 블로킹 호출이 끊긴다. 시험 `[2b]` 가 정확히 이 경우를 만든다

## 4. 변형 (부록)

### 변형 B — `SOCK_SEQPACKET` / `SOCK_DGRAM`

- Unix 소켓은 경계를 보존하는 타입이 있다. 프레이밍 없이 같은 일을 하면 무엇이 달라지고 무엇을 잃나 (크기 제한, 부분 수신 없음)

### 변형 C — 길이 가변 → 구분자 (줄 단위)

- `\n` 으로 끝나는 텍스트 프로토콜. 구분자가 내용에 들어오면? (이스케이프) 줄이 끝없이 길면? (최대 길이)
