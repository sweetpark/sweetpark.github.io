## 1. 이론 요약

```
data[cap]  (cap = 2의 거듭제곱)

  head(받는 쪽이 쓴다)             tail(보내는 쪽이 쓴다)
    ▼                                ▼
 ...[len|내용 ][len|내용 ]  ........  [        ]...
        └ 한 메시지 = 4바이트 길이 + 내용. 링 끝에서 둘로 쪼개져 저장될 수 있다

 head, tail 은 **감기지 않고 계속 커진다**   실제 자리 = 위치 & (cap - 1)
 쌓인 양 = tail - head   (unsigned 뺄셈 → 2^64 를 넘어도 맞다)
 빈 통로: tail == head   /   가득: tail - head == cap
```

| 순서 | 보내는 쪽 | 받는 쪽 |
| :--- | :--- | :--- |
| 1 | `tail` 읽기 (내 것), `head` 를 **acquire** 로 읽기 | `head` 읽기 (내 것), `tail` 을 **acquire** 로 읽기 |
| 2 | 자리 확인: `cap - (tail - head) >= 4 + len` — 모자라면 `-EAGAIN`, **아무것도 안 씀** | 쌓인 양 확인: 0 이면 `-EAGAIN` |
| 3 | 길이 4바이트 + 내용 복사 (링 끝에서 **두 번에 나눠**) | 길이 칸 읽기 → **검증** (0 이거나 쌓인 양보다 크면 `-EIO`) → 버퍼가 작으면 `-EMSGSIZE` (**`head` 안 움직임**) |
| 4 | `tail` 을 **release** 로 올려 공개 | 내용 복사 후 `head` 를 **release** 로 올려 자리 반환 |

```diff
- tail = (tail + n) % cap;                    /* 감아서 저장 → 가득/빔 구분이 모호 */
- memcpy(data + tail, src, n);                /* 끝에서 넘치면 링 밖을 덮어씀 */
+ ring_put(c, tail, src, n);                  /* 위치 & (cap-1), 두 번에 나눠 복사 */
+ __atomic_store_n(&c->tail, tail + n, __ATOMIC_RELEASE);
```

## 2. 재현 — 어디서 뚫리나

| 상황 | 틀린 코드의 결과 | 이유 |
| :--- | :--- | :--- |
| cap 64 에서 메시지 14바이트씩 5개 | 5번째가 반쯤 쓰이고 실패 / 받는 쪽이 반쪽 메시지 | 자리 확인 전에 썼다 |
| 길이 칸이 링 끝 2바이트 앞에 걸림 | 길이가 쓰레기 | 4바이트 길이 칸은 쪼개지지 않는다고 가정했다 |
| `head`/`tail` 이 `ULONG_MAX` 를 넘어 0 으로 | 가득/빔 판정이 뒤집힘 | `tail < head` 같은 비교를 썼다 (뺄셈을 써야 한다) |
| 받는 쪽 버퍼가 작음 | 메시지가 사라짐 | 실패했는데 `head` 를 움직였다 |
| 보내는 쪽이 죽다 말아 길이 칸이 `0xFFFFFFFF` | 받는 쪽이 링 밖을 읽음 | 남이 쓴 길이를 믿었다 |
| 생산자 둘 | 서로의 `tail` 을 덮어씀 | 이 설계는 **SPSC** 다. 보내는 쪽이 둘이면 통로를 둘로 나누거나 락을 건다 |

## 3. 주의해야 할 점

1. **락이 없는 것은 "쓰는 쪽이 하나"이기 때문이다**
	- `tail` 은 생산자만, `head` 는 소비자만 쓴다. 서로의 변수는 **읽기만** 한다
	- 이 약속이 깨지는 순간(생산자 둘) 락이 필요해진다 → P113
1. **release/acquire 는 장식이 아니다**
	- x86 은 쓰기 순서를 거의 보존해서 틀려도 잘 돈다. ARM 에서는 터진다
	- 컴파일러도 순서를 바꿀 수 있어서 x86 에서도 최적화에 따라 터질 수 있다
1. **바쁜 대기는 시험용이다**
	- `sched_yield()` 로 양보하며 `-EAGAIN` 을 재시도한다. 실제 데몬은 `eventfd` / 세마포어 / `poll` 로 깨운다 (CPU 100% 방지)
1. **프로세스 사이라서 포인터가 없다**
	- 통로의 모든 상태가 공유메모리 안에 있다. `cap` 도 안에 있다 (P112 의 "포인터 대신 오프셋")
1. **P104 와 같은 링 버퍼, 다른 점**
	- P104 는 한 프로세스 안의 스레드 사이 + 가득 차면 **버린다**. 여기는 프로세스 사이 + 가득 차면 `-EAGAIN` 으로 **돌려준다**(호출자가 재시도)

## 4. 변형 (부록)

### 변형 B — 여러 생산자 (MPSC)

- 통로를 생산자마다 하나씩 두고 소비자가 돌아가며 읽는다 / 또는 `tail` 을 `compare-and-swap` 으로 예약

### 변형 C — 소비자가 죽었다가 다시 뜬다

- `head` 가 공유메모리에 있으므로 재기동한 소비자가 이어서 읽는다. 읽다가 죽었다면 그 메시지는 어떻게 되나? (`head` 를 올리기 전에 죽었으면 **다시 읽게 된다** → 중복 처리 대비)

### 변형 D — 길이 가변 → 고정 슬롯

- 슬롯 크기를 고정하면 쪼개짐이 없어진다. 대신 작은 메시지에서 공간을 낭비한다. 어느 쪽이 맞을 때가 언제인가?
