## 1. 이론 요약

```
pthread_mutex_lock()
  ├─ 0                → 정상. 락 획득
  ├─ EOWNERDEAD       → 락은 **이미 내 것**. 단, 이전 주인이 죽었고 데이터는 반쯤 바뀌었을 수 있다
  │      ① 데이터 복구 (undo 로그로 되돌림)
  │      ② pthread_mutex_consistent()   ← 빼고 unlock 하면 락이 영구히 ENOTRECOVERABLE
  │      ③ 락을 쥔 채 호출자에게 "복구했다"를 알림 (이 문제에서는 반환 1)
  └─ ENOTRECOVERABLE  → 복구를 하지 않고 풀어 버린 락. 이 락은 못 쓴다 (세그먼트를 새로 만들어야)
```

| 항목 | 규칙 |
| :--- | :--- |
| 속성 | `PTHREAD_PROCESS_SHARED` (프로세스 사이) + `PTHREAD_MUTEX_ROBUST` (죽은 주인 감지) |
| `EOWNERDEAD` | 에러처럼 생겼지만 **락 획득 성공의 한 종류** |
| 복구 | 락은 "죽었다"만 알려 준다. **되돌릴 정보는 데이터 쪽에 기록**해 둔다 (undo 로그, WAL 과 같은 생각 → P110) |
| 불변식 | 락 **밖**에서는 항상 `a + b == total`. 락 **안**에서만 잠깐 깨질 수 있다 |
| 실패 경로 | `E_FUNDS` 로 돌아갈 때도 락을 푼다 |

```diff
- pthread_mutex_init(&s->mu, NULL);                     /* private + 비-robust */
- pthread_mutex_lock(&s->mu);                           /* 죽은 주인을 영원히 기다린다 */
+ pthread_mutexattr_setpshared(&at, PTHREAD_PROCESS_SHARED);
+ pthread_mutexattr_setrobust(&at, PTHREAD_MUTEX_ROBUST);
+ rc = pthread_mutex_lock(&s->mu);
+ if (rc == EOWNERDEAD) { undo(s); pthread_mutex_consistent(&s->mu); return 1; }
```

## 2. 재현 — 어디서 뚫리나

| 상황 | 틀린 코드의 결과 | 이유 |
| :--- | :--- | :--- |
| 이체 도중(`a` 만 줄이고 `b` 는 아직) 소유자가 SIGKILL | 비-robust: 다음 호출이 **영원히 멈춤** | 락이 잠긴 채 남는다 |
| 같은 상황, robust 지만 `EOWNERDEAD` 를 에러로 반환 | 락을 쥔 채 나가서 **그다음부터 모두 멈춤** | 락은 이미 내 것인데 풀지 않았다 |
| 같은 상황, `consistent` 만 호출하고 복구는 안 함 | 락은 풀리지만 `a + b != total` 인 채로 운영 | "죽었다"는 알림을 데이터 정합성으로 착각 |
| `consistent` 없이 `unlock` | 이후 `lock` 이 `ENOTRECOVERABLE` | 락이 영구히 못 쓰는 상태 |
| `acct_move` 가 `acct_lock` 의 `1` 을 실패로 처리 | 복구 직후 이체가 실패하고 락을 쥔 채 반환 | `1` 은 성공의 한 종류 |

## 3. 주의해야 할 점

1. **"`PROCESS_SHARED` 를 빼도 돌아간다"는 착각**
	- 리눅스에서는 private 뮤텍스가 다른 프로세스에서도 **우연히** 돈다. 시험으로는 잡히지 않는다
	- 깨우기가 누락되는 경우에만 멈추므로 재현이 안 되는 장애가 된다 → 코드 리뷰에서 속성을 본다
1. **장애 때 보는 법**
	- 프로세스들이 모두 `S` (sleep) 상태이고 CPU 를 안 쓴다 → `strace -p <pid>` 로 `futex(... FUTEX_WAIT ...)` 에서 멈춰 있으면 락 대기
	- `ipcs -m` 은 정상(세그먼트는 그대로). 죽은 프로세스의 `lpid` 만 단서가 된다 (공유메모리 지도)
1. **undo 로그 자체도 락 안에서 써야 한다**
	- `old_a`, `old_b`, `in_tx = 1` 을 쓰는 중에 죽으면? 순서가 중요하다: **로그(`old_a`, `old_b`)를 먼저 다 쓰고** 마지막에 `in_tx` 를 올려야 한다. `in_tx` 를 먼저 올리면, 그 직후 죽었을 때 복구가 **쓰이지 않은 쓰레기 `old_*`** 로 되돌린다
	- 끝낼 때는 반대: 데이터를 다 바꾼 **뒤에** `in_tx = 0`
1. **복구가 가능한 것과 불가능한 것**
	- 불변식을 되돌릴 수 있는 설계(undo 로그)라서 가능했다
	- 되돌릴 수 없으면 `consistent` 를 부르지 않고 `unlock` 해서 락을 `ENOTRECOVERABLE` 로 만들고, 상위에서 세그먼트를 새로 만든다 (**의도적인 포기**)

## 4. 변형 (부록)

### 변형 B — 복구하는 쪽도 죽는다

- 복구 도중(undo 중)에 죽으면 다음 사람이 또 `EOWNERDEAD` 를 받는다. undo 가 **여러 번 실행돼도 같은 결과**(멱등)인가?

- `sem_t` (pshared) 와 `flock` 은 죽은 소유자를 어떻게 다루나? (robust 가 없는 `sem_t` 는 `SEM_UNDO` 가 System V 세마포어에만 있다)
