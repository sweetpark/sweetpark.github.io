# D9. 종합 — 요구사항 한 장을 동작하는 데몬으로

> **쓰는 템플릿**: 1 ~ 6번 전부
> **목표 시간**: 1회차 이틀(실작업 6h) / 2회차 4h / **3회차 2h**
> D0~D8 을 **각 3회차까지 끝낸 뒤**에 한다. 여기서 막히면 막힌 드릴로 되돌아간다 — 그게 이 드릴의 용도다.

---

## 0. 합격의 정의

> **요구사항 한 장을 받아, 설계서 4장과 동작하는 데몬과 시험을 혼자서 끝까지 만든다.**

"C를 안다"가 아니라 **"혼자 끝까지 간다"** 가 기준이다.

---

## 1. 요구사항 — 변형 A: 세션 상태 관리 데몬

> [!QUOTE] 요구사항서 (전문)
> **세션 등록·갱신·해제 요청을 받아 상태를 관리하고, 응답 없는 세션을 자동 만료시키는 상주 프로세스.**
>
> **1) 프로토콜**
> - 전송: UDP. 메시지는 **D4 의 12바이트 고정 헤더 + D5 의 TLV body + 체크섬 2바이트**.
> - `Type`: `1=REGISTER`, `2=UPDATE`, `3=DEREGISTER`, `4=HEARTBEAT`, `129~132`=각 응답(`요청+128`).
> - body IE: `0x01 SessionId(4,M)` · `0x02 Cause(1, 응답만 M)` · `0x10 UeName(0~32,O)` · `0x20 Timestamp(8,O)` · `0x40 Ttl(2,O, 초)`.
> - 모르는 IEI 는 **건너뛰고 응답에 그대로 echo**.
>
> **2) 동작**
> - `REGISTER`: 세션을 `ACTIVE` 로 생성. 이미 있으면 **갱신**하고 `Cause=1(ALREADY_EXIST)`.
> - `UPDATE` / `HEARTBEAT`: 만료 시각을 `now + ttl` 로 연장. 없는 세션이면 `Cause=4(NOT_FOUND)`.
> - `DEREGISTER`: 세션 제거. 없으면 `Cause=4`.
> - `ttl` 기본 30초, 범위 5~3600.
> - **만료 감시**: 1초마다 순회해 만료된 세션을 `CLOSING` → 1초 뒤 제거. 만료 시 로그 1줄.
> - 동시 세션 최대 **10,000**. 초과 시 `Cause=6(NO_RESOURCE)`.
> - 세션 조회는 **해시 테이블**(버킷 1024, `session_id % 1024`).
>
> **3) 운영**
> - 설정 파일: `listen_port`, `worker_num`(1~64), `log_level`, `session_max`, `default_ttl`.
> - `SIGHUP`: `log_level`, `default_ttl` 만 재적재.
> - `SIGTERM`/`SIGINT`: **graceful shutdown** — 수신 중단 → 큐 소진 → 스레드 종료 → 자원 해제. 최대 5초.
> - 1초마다 통계 로그: `active=N expired=N rx=N tx=N drop=N`.
> - **어떤 입력에도 프로세스가 죽지 않는다.**
>
> **4) 성능 (참고선)**
> - 단일 노드에서 **초당 10,000 메시지** 처리 시 CPU 1코어 이하, 메모리 증가 없음(30분 연속).

### 회차별 변형

| 회차 | 변형 | 핵심 차이 |
| :--- | :--- | :--- |
| **A (1회차)** | 세션 관리 데몬 | UDP + 해시 + 만료 감시 |
| **B (2회차)** | **과금 집계기** | TCP 수신 + **파일 저널**(fseek·파일 락) + 5분 단위 집계 + 재기동 시 저널 복구 |
| **C (3회차)** | **프로토콜 릴레이** | 양방향 TCP 중계 + 요청-응답 매칭(check-in/out) + 타임아웃 재전송 1회 |

## 2. 산출물 — 세 묶음

### ① 설계서 (D6 그대로, 네 장)

```text
d9/design.md
  1. 블록도        — 프로세스 내부 구성 (수신 / 큐 / 워커 / 세션표 / 감시 스레드)
  2. sequence      — REGISTER 정상 · 중복 · 만료 3종
  3. erDiagram     — session_t / 해시 버킷 / 통계
  4. flowchart     — handle_register() 내부 (종료점마다 Cause)
  5. stateDiagram  — IDLE → ACTIVE → CLOSING → (삭제)
```

### ② 코드

```text
d9/src/
  common.h  guard.h  log.h        ← D0
  cfg.c/.h                        ← D3 (설정 로더)
  msg.c/.h                        ← D4 (헤더 pack/unpack)
  tlv.c/.h                        ← D5 (body 파서/생성)
  session.c/.h                    ← D2 (구조체) + 해시 테이블
  jobq.c/.h                       ← D7 (스레드 안전 큐)
  daemon.c                        ← D7 (main / poll / 시그널)
  handler.c                       ← D1·D3 (요청 타입별 처리 함수)
```

> [!TIP] 파일 순서가 곧 드릴 순서다
> 새로 만드는 코드는 **`handler.c` 와 `session.c` 뿐**이다. 나머지는 앞 드릴 결과를 **그대로 가져온다.**
> 가져다 쓸 수 없으면, 그 드릴을 다시 해야 한다는 신호다.

### ③ 시험

| 계층 | 내용 |
| :--- | :--- |
| 단위 | 함수마다 정상 / 경계 / NULL 3개 |
| 왕복 | `pack→unpack`, `build→parse` (모르는 IE 포함) |
| 자르기 | 수신 버퍼를 0~len-1 로 잘라 전부 비크래시 |
| 실패 주입 | `malloc` N번째 실패 → 누수 0 (D3 방식) |
| 시나리오 | 아래 인수 시험 8종 |

---

## 3. 인수 시험 (Acceptance) — 8개 전부 통과해야 합격

| # | 시험 | 방법 | 통과 기준 |
| :--- | :--- | :--- | :--- |
| 1 | 정상 등록·갱신·해제 | 클라이언트 스크립트 | 응답 Cause=0, 상태 로그 일치 |
| 2 | 중복 등록 | REGISTER 2회 | 두 번째 `Cause=1`, 세션 1개 유지 |
| 3 | 없는 세션 갱신 | UPDATE | `Cause=4`, 크래시 없음 |
| 4 | **자동 만료** | ttl=5 등록 후 대기 | 5~7초 사이 만료 로그 1줄, `active` 감소 |
| 5 | **쓰레기 입력** | 무작위 바이트 1000개 | 전부 drop + WRN, 프로세스 생존 |
| 6 | **정원 초과** | 10,001번째 등록 | `Cause=6`, 메모리 증가 없음 |
| 7 | **graceful shutdown** | 부하 중 SIGTERM | 5초 내 exit 0, **누수 0**, 큐 유실 0 |
| 8 | **30분 연속 부하** | 초당 10k | RSS 증가 없음(±1MB), 응답 지연 안정 |

```bash
# 5번: 쓰레기 입력
for i in $(seq 1 1000); do head -c $((RANDOM % 64)) /dev/urandom | nc -u -w0 127.0.0.1 9000; done
pgrep -f d9_sessiond > /dev/null && echo "생존 ✔" || echo "죽음 ✘"

# 8번: 누수 관찰 (30분)
while true; do ps -o rss= -p $(pgrep -f d9_sessiond); sleep 60; done
```

> [!IMPORTANT] 8번이 진짜 시험이다
> 기능은 대부분 첫날에 된다. **30분 돌렸을 때 메모리가 안 늘어나는지**가 실무와 습작을 가른다.
> RSS 가 우상향하면 **해제 경로 하나가 빠진 것**이다. 실패 주입 시험으로 찾는다.

## 4. 진행 계획 (1회차 기준)

| 구간 | 시간 | 하는 일 | 끝났다는 신호 |
| :--- | :--- | :--- | :--- |
| ① 표 3장 | 30분 | 메시지별 입력·출력·에러 표 | 에러 표에 Cause 6종이 다 있다 |
| ② 설계서 4장 | 45분 | D6 그대로 | flowchart 종료점마다 Cause |
| ③ 부품 이식 | 30분 | D0·D3·D4·D5·D7 결과 복사 + 빌드 | 빈 `main` 이 뜨고 종료된다 |
| ④ 세션 저장소 | 60분 | 해시 테이블 + `session_t` + 만료 필드 | 단위 시험 통과 |
| ⑤ 핸들러 4종 | 90분 | `handle_register/update/dereg/hb` | 시나리오 1~3 통과 |
| ⑥ 만료 감시 | 45분 | 감시 스레드 + `CLOSING` 전이 | 시나리오 4 통과 |
| ⑦ 강건성 | 60분 | 자르기·쓰레기·정원초과·실패주입 | 시나리오 5~7 통과 |
| ⑧ 부하·정리 | 60분 | 30분 부하 + 회고 작성 | 시나리오 8 통과 |

> [!WARNING] ③에서 이식이 안 되면 멈추고 돌아간다
> 앞 드릴 코드를 **손보지 않고 붙일 수 없다면** 그 드릴의 3회차가 덜 된 것이다.
> 여기서 새로 짜기 시작하면 이 드릴은 종합이 아니라 그냥 큰 숙제가 된다.

## 6. 회고 — 이걸 써야 다음 사이클이 짧아진다

끝나고 **10분** 안에 아래를 채운다. 길게 쓰지 않는다.

```markdown
## D9-A 회고 (YYYY-MM-DD)

### 어디서 제일 오래 막혔나 (한 줄)
-

### 그건 어느 드릴의 내용이었나
- D_ : 이유 →

### 템플릿을 안 보고 친 비율 (체감 %)
- 1번 골격 __% / 2번 구조체 __% / 3번 바이트 __% / 4번 데몬 __%

### 다음 사이클에서 되돌아갈 드릴
- D_ 를 __회차부터

### 템플릿 문서에 추가하고 싶은 것 (있으면 실제로 반영)
-
```

> [!TIP] 회고의 마지막 줄이 제일 중요하다
> 드릴을 돌다 보면 **템플릿 문서 자체의 빈칸**이 보인다. 그때 [c코드 템플릿](../../c코드%20템플릿/c코드%20템플릿%20목록.md) 을 고친다.
> 템플릿이 좋아지면 다음 회차가 또 빨라진다. **이게 이 체계의 복리 구간이다.**
