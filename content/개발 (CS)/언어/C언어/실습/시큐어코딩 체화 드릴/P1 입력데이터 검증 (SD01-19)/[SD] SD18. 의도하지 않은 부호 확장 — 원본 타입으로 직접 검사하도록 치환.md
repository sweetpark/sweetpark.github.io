## 1. 이론 요약

| 항목 | 내용 |
|---|---|
| **신뢰 경계** | `int` → 검증 없이 → `short` → `unsigned` 로 연쇄 변환 |
| **공격 시나리오** | 오버플로우로 음수가 된 값을 `unsigned` 로 옮기면 40억대의 값이 되어 배열 접근이 범위를 크게 벗어나고, 권한 등급 계산에서는 음수가 큰 양수로 뒤집혀 권한 검사를 우회한다. |
| **치환 규칙** | 크기가 다른 타입 간 대입 전 명시적 타입 체크, `unsigned` 변환은 항상 "음수 여부 + 상한" 검사 이후에만 수행. |
| **주의** | 형 변환 전 "음수일 수 있는가"를 먼저 묻고, 뺄셈은 결과가 0 아래로 내려가지 않음을 확인한 뒤 수행하라. |
| **자세한 설명** | [Part 1-4. 정수·타입변환 계열 — 18. 의도하지 않은 부호 확장](개발%20%28CS%29/언어/C언어/시큐어코딩/Part%201.%20입력데이터%20검증%20및%20표현/[시큐어코딩]%201-4.%20정수·타입변환%20계열.md#18-의도하지-않은-부호-확장-cwe-194) (Bad/Good 전체 코드, 보충) |

```diff
- s = (short)id;              /* int -> short, 음수화 가능 */
- if (s > 256) return -1;     /* 음수는 이 검사를 통과해버린다 */
- sz = (unsigned)s;           /* 음수 -> unsigned, 거대한 값 */
- return info[sz];
+ if (id < 0 || (size_t)id >= info_size) return -1;   /* 원본 int로 직접, 축소 변환 없이 검사 */
+ return info[id];
```

## 2. 재현 — 신뢰 경계와 공격 입력

**공격 입력표**

| `id` | Bad 결과 | 이유 |
| :--- | :--- | :--- |
| 10 (정상) | 정상 값 반환 | 유효 범위 |
| **40000** | **SIGSEGV로 크래시** | `short` 로 잘리며 `-25536` 이 되어 `s > 256` 검사를 통과, 이후 `unsigned` 로 뒤집혀 `info[4294941760]` 접근 |

---

## 3. 주의해야 할 점

1. **`short s = (short)id;` 를 그대로 두고 `if (s < 0)` 검사만 추가**
	- 이미 축소 변환이 일어난 **뒤**에 검사하는 것이라 늦다.
	- 축소 자체를 하지 않는 것이 유일한 확실한 해법이다
1. **`unsigned` 변환 직전에만 `if (s < 0) return -1;` 을 넣고 원본 `id` 상한(300)은 검사 안 함**
	- 부호 문제는 막아도, `id` 가 300~32767 사이의 정상 양수 `short` 범위라면 여전히 배열을 벗어난다.
	- 상한 검사는 별개로 필요하다
1. **이 항목도 SD17처럼 UBSan이 잡아줄 거라 기대함**
	- 대입에 의한 축소 변환은 구현정의이지 UB가 아니다
		- 새니타이저에 기대지 말고 **코드 자체를 정확히** 짜야 하는 항목이다

## 4. 변형 (부록)

같은 치환 규칙을 다른 소재로 다시 치는 문제들이다. 저장소에는 변형 A 만 문제로 있다.

### 변형 B — 권한 등급 비교

`short level = (short)userLevel;` 로 권한 등급을 비교하는 코드에서, 음수로 뒤집힌 값이 "가장 높은 권한"으로 오판되는 시나리오

### 변형 C — 뺄셈 결과가 음수가 되지 않는지 사전 확인

PDF 원문의 `if (userLevel > penalty) userLevel -= penalty; else userLevel = 0;` 패턴을 직접 짜보고, 이 검사가 왜 필요한지 SD18의 문맥에서 설명해본다
