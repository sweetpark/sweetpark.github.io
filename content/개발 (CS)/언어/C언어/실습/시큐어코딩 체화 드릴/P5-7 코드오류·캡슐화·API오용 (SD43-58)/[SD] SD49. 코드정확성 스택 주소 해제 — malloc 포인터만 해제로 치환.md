## 1. 이론 요약

| 항목 | 내용 |
|---|---|
| **신뢰 경계** | (해당 없음: free 대상 오분류가 결함) |
| **공격 시나리오** | 스택 변수나 `strtok()` 반환값처럼 힙에 할당되지 않은 주소를 `free()` 하면 힙 메타데이터가 손상되어 즉시 abort 되거나 임의 코드 실행으로 악용될 수 있다. |
| **치환 규칙** | `malloc`/`calloc`/`realloc` 으로 얻은 포인터만 `free()` 대상. 라이브러리 함수 반환값은 "할당 여부"를 문서에서 먼저 확인. |
| **주의** | free()의 유일한 정당한 인자는 "내가 malloc 계열로 받은 포인터"뿐이다. |
| **자세한 설명** | [Part 5. 코드 오류 — 7. 코드정확성: 스택 주소 해제](개발%20%28CS%29/언어/C언어/시큐어코딩/[시큐어코딩]%20Part%205.%20코드%20오류.md#7-코드정확성-스택-주소-해제-cwe-730) (Bad/Good 전체 코드, 보충) |

```diff
- char p[10];
- free(p);                          /* 스택 주소 해제 -> 비정상 동작 */
+ char *p = (char *)malloc(10);
+ if (!p) return -1;
+ /* 사용 */
+ free(p);                          /* malloc으로 받은 포인터만 해제 */
```

## 2. 재현 — 신뢰 경계와 공격 입력

**신뢰 경계** : 검증 없이 흘러가는 곳

| 값 | 출처 | 검증 없이 흘러가는 곳 |
| :--- | :--- | :--- |
| (해당 없음) | — | `free()` 대상 오분류(스택 주소를 힙 포인터로 착각) 자체가 결함이다 |

**공격 입력표**

| 상황 | Bad 결과 | 이유 |
| :--- | :--- | :--- |
| 스택 배열 `p`를 그대로 `free(p)` | **`bad-free`로 크래시**(`expect_crash`가 감지) | `free()`가 관리하는 힙 메타데이터에 스택 주소가 없으니 즉시 위반이 드러난다 |
| 같은 상황(Good) | 정상 종료 | `malloc`으로 받은 포인터만 `free`한다 |

## 3. 주의해야 할 점

1. **"포인터가 유효해 보이니 괜찮다"고 판단**
	- `free()`의 정당성은 "가리키는 메모리가 유효한가"가 아니라 **"malloc 계열이 반환한 그 주소인가"**다.
	- 스택 주소도 함수가 살아있는 동안은 완전히 유효한 메모리지만 `free()` 대상은 아니다
1. **라이브러리 함수의 반환값을 볼 때마다 "할당 여부"를 확인하지 않음**
	- `strtok()`, `getenv()`, `ctime()` 등 많은 표준 함수가 "내부 정적 버퍼" 또는 "입력 문자열 내부"를 가리키는 포인터를 반환한다.
	- 반환값을 받을 때마다 매뉴얼에서 "할당된 메모리인가"를 확인하는 습관이 필요하다
1. **`free()` 이후 포인터를 `NULL`로 안 만듦(이 드릴 자체보단 습관 문제)**
	- 이 항목의 핵심은 아니지만, `free(p)` 직후 `p = NULL;`을 습관화하면 실수로 같은 포인터를 다시 `free()`하는 이중 해제(변형 C)를 예방하는 데 도움이 된다

## 4. 변형 (부록)

같은 치환 규칙을 다른 소재로 다시 치는 문제들이다. 저장소에는 변형 A 만 문제로 있다.

### 변형 B — `strtok()` 반환값을 `free()`하는 실수로 변형

- 가이드 원문처럼 `strtok(str, " ,.-")`의 반환값을 순회하며 실수로 `free(pch)`를 호출하는 버전을 만들어본다
	- `strtok`은 원본 문자열 내부를 가리킬 뿐 아무것도 할당하지 않는다는 걸 크래시로 확인한다

### 변형 C — 이중 해제(double free)로 확장

이번엔 진짜 `malloc` 포인터를 두 번 연속 `free()`하는 함수를 만들어, "malloc 포인터라도 한 번만 해제해야 한다"는 별개의 규칙까지 재현한다
