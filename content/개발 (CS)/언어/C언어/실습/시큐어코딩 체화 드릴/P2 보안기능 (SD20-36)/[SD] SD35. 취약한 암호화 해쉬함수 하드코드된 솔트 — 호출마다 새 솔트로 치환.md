## 1. 이론 요약

| 항목 | 내용 |
|---|---|
| **신뢰 경계** | 소스 코드 상수(`"xp"`) → 그대로 → 해쉬 솔트 |
| **공격 시나리오** | 공격자가 하드코드된 솔트를 알아내면 그 솔트를 적용한 레인보우 테이블을 한 번 만들어 모든 사용자 해쉬값을 역으로 계산할 수 있다. |
| **치환 규칙** | 솔트 리터럴 삭제 → 호출마다 CSPRNG로 새로 생성해 인자로 전달, 해쉬값과 함께 저장. |
| **주의** | 솔트는 비밀이 아니라 "매번 달라야 하는 값"이다. 고정된 순간 솔트로서의 존재 이유가 사라진다. |
| **자세한 설명** | [Part 2-3. 암호화 계열 — 16. 취약한 암호화 해쉬함수: 하드코드된 솔트](개발%20%28CS%29/언어/C언어/시큐어코딩/Part%202.%20보안기능/[시큐어코딩]%202-3.%20암호화%20계열.md#16-취약한-암호화-해쉬함수-하드코드된-솔트-cwe-326) (Bad/Good 전체 코드, 보충) |

```diff
- unsigned get_salt_bad(void) { return 0xC0FFEE; }             /* 항상 같은 솔트 */
+ if (getrandom(raw, sizeof(raw), 0) != (ssize_t)sizeof(raw)) return -1;
+ memcpy(out_salt, raw, sizeof(unsigned));                      /* 호출마다 새 솔트 */
```

## 3. 주의해야 할 점

1. **"솔트 하드코딩"과 "키 하드코딩"(SD26)을 같은 문제로 뭉뚱그림**
	- 키는 비밀이라 저장소에서 안전하게 보관해야 하지만, 솔트는 **비밀이 아니라 매번 새로 만들어야 하는 값**이다.
	- 대응 방식이 다르다(SD26=키 저장소 조회, SD35=매번 신규 생성)
1. **솔트를 `rand()` 로 생성(SD31 이전 방식으로 회귀)**
	- 솔트도 예측 가능하면 사전 계산 공격의 여지가 생긴다.
	- SD31에서 이미 확립한 `getrandom` 패턴을 그대로 가져온다
1. **Part 2-3을 여기서 끝내고 SD32·33·35를 하나로 잇는 변형 B를 건너뜀**
	- 실전에서는 이 세 항목이 **한 함수 안에서 동시에** 지켜져야 한다.
	- 따로따로는 이해했지만 합쳐서 짜보지 않으면 실무에서 순서를 놓치기 쉽다

## 4. 변형 (부록)

같은 치환 규칙을 다른 소재로 다시 치는 문제들이다. 저장소에는 변형 A 만 문제로 있다.

### 변형 B — SD33·SD26과 전부 결합

"계정 생성 시 새 솔트 발급(SD35) → 그 솔트로 패스워드 해시(SD33) → 결과를 저장(SD32)"까지 하나의 함수 체인으로 완성 — Part 2-3 전체를 관통하는 최종 통합 드릴

### 변형 C — 솔트 크기를 16바이트(128비트)로 확장

`unsigned`(보통 4바이트) 대신 `unsigned char[16]` 배열로 바꿔 실전 수준의 솔트 크기를 다룬다
