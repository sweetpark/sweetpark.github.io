## 1. 이론 요약

| 항목 | 내용 |
|---|---|
| **신뢰 경계** | 소스 코드 상수 → 그대로 → DB 접속 인증 |
| **공격 시나리오** | `strings` 명령 한 번으로 DB 계정·관리자 패스워드가 드러나고, 배포된 모든 설치본이 동일한 비밀번호를 공유한다. 변경하려면 재컴파일·재배포가 필요하다. |
| **치환 규칙** | 소스 상수 패스워드 삭제 → 함수 인자로 전달받거나 설정파일/저장소에서 암호화된 값을 로드. |
| **주의** | 소스에 박힌 비밀번호는 바이너리에도 남는다. 패스워드는 코드가 아니라 설정·저장소에서 암호화된 상태로 로드하라. |
| **자세한 설명** | [Part 2-2. 자격증명 관리 계열 — 5. 하드코드된 패스워드](개발%20%28CS%29/언어/C언어/시큐어코딩/Part%202.%20보안기능/[시큐어코딩]%202-2.%20자격증명%20관리%20계열.md#5-하드코드된-패스워드-cwe-259) (Bad/Good 전체 코드, 보충) |

```diff
- snprintf(out, out_size, "server=%s;user=%s;pw=%s", server, user, "asdf");   /* 상수 */
+ void db_connect_good(const char *server, const char *user, const char *passwd, ...)
+ snprintf(out, out_size, "server=%s;user=%s;pw=%s", server, user, passwd);   /* 인자로 전달 */
```

**공격 입력표**

| 상황 | Bad 결과 | 이유 |

| 어떤 서버·사용자로 호출해도 | **`pw=asdf` 로 고정** | 패스워드가 소스에 박혀 있어 절대 안 바뀐다 |

---

## 3. 주의해야 할 점

1. **Good에서도 기본값(`"default_pw"` 등)을 상수로 둠**
	- "기본값"이라는 이름표만 붙였을 뿐 여전히 하드코딩이다.
	- 인자가 없으면 실패하도록 설계한다
1. **두 번째 시험(`test_bad_cannot_be_changed`)을 생략**
	- 한 번만 호출해서는 "우연히 그 값이었다"와 "항상 그 값이다"를 구분할 수 없다.
	- 서로 다른 조건으로 최소 두 번 호출해서 비교하는 게 이 계열 검증의 핵심이다
1. **`strstr` 대신 `strcmp` 로 전체 문자열을 비교**
	- 접속 문자열에 서버·사용자 정보가 함께 있어 완전 일치 비교가 깨지기 쉽다.
	- 확인하려는 부분 문자열만 `strstr` 로 검사한다

## 4. 변형 (부록)

같은 치환 규칙을 다른 소재로 다시 치는 문제들이다. 저장소에는 변형 A 만 문제로 있다.

### 변형 B — API 키를 헤더에 싣기

`Authorization: Bearer <key>` 헤더 문자열을 만드는 함수로 변형

### 변형 C — 설정 파일에서 로드하는 버전으로 확장

`db_connect_good` 이 인자로 패스워드를 직접 받는 대신, "설정 파일 경로"를 받아 그 파일에서 읽어오는 형태(`load_password_from_file`)로 한 단계 더 발전시킨다
