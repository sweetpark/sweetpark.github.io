## 1. 이론 요약

| 항목 | 내용 |
|---|---|
| **신뢰 경계** | 소스 코드 상수(`"root"`, `"DBAdmin"`) → 그대로 → 인증 계정 |
| **공격 시나리오** | 프로그램만 실행할 수 있으면 누구나 인증 없이 DB에 접근할 수 있고, 바이너리 문자열 추출로 계정과 패스워드가 노출된다. |
| **치환 규칙** | 계정명 상수 삭제 → 외부(설정·자격증명 저장소)에서 로딩·검증하는 별도 루틴으로 획득. |
| **주의** | 하드코드된 계정은 "고칠 수 없는 백도어"다. 바꾸려면 재컴파일과 전체 정지가 필요하다. |
| **자세한 설명** | [Part 2-2. 자격증명 관리 계열 — 6. 하드코드된 사용자 계정](개발%20%28CS%29/언어/C언어/시큐어코딩/Part%202.%20보안기능/[시큐어코딩]%202-2.%20자격증명%20관리%20계열.md#6-하드코드된-사용자-계정-cwe-255) (Bad/Good 전체 코드, 보충) |

```diff
- snprintf(out, out_size, "user=%s;pw=%s", "root", passwd);   /* 계정명이 상수 */
+ void db_login_good(const char *user, const char *passwd, ...)
+ snprintf(out, out_size, "user=%s;pw=%s", user, passwd);      /* 계정명도 인자로 */
```

## 2. 재현 — 신뢰 경계와 공격 입력

**공격 입력표**

| 상황 | Bad 결과 | 이유 |
| :--- | :--- | :--- |
| 패스워드를 무엇으로 바꿔도 | **`user=root` 로 고정** | 계정명이 소스에 박혀 있다 |

---

## 3. 주의해야 할 점

1. **SD24와 이 항목을 같은 결함이라고 뭉뚱그려 하나만 체화하고 넘어감**
	- CWE 번호가 다르고(259 vs 255) "무엇이 하드코딩됐는가"가 다르다.
	- Part 2 전체를 관통하는 "CWE 두 자리를 대상으로 구분하라"는 원칙을 여기서 직접 확인한다
1. **계정명은 인자화했지만 여전히 함수 안에서 `"root"` 를 기본값으로 씀**
	- 인자를 안 넘겼을 때만 몰래 하드코딩 값으로 대체하는 것도 같은 결함이다.
	- 기본값 자체를 두지 않는다

## 4. 변형 (부록)

같은 치환 규칙을 다른 소재로 다시 치는 문제들이다. 저장소에는 변형 A 만 문제로 있다.

### 변형 B — 다중 환경(운영/스테이징) 계정 분리

환경별로 계정명이 달라야 하는데, Bad는 환경이 바뀌어도 같은 계정을 쓴다는 걸 재현

### 변형 C — 계정+패스워드 둘 다 인자화한 뒤, 그 값이 실제로는 SD24의 파일 로드 함수에서 온 것으로 연결

SD24 변형 C와 이어붙여, "계정명·패스워드 둘 다 하나의 설정 로더에서 나온다"는 실무 구조를 완성
