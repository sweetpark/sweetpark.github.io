## 1. 이론 요약

| 항목 | 내용 |
|---|---|
| **신뢰 경계** | 설정 파일(config) → 평문으로 → DB 인증 |
| **공격 시나리오** | 설정파일 하나만 유출되면 DB 계정과 사용자 패스워드 전체가 노출되고, 자격증명 재사용 공격으로 확산된다. |
| **치환 규칙** | 설정파일 저장 값은 암호화, 인증 목적이면 복호화 대신 일방향 해쉬(솔트 포함) 비교. |
| **주의** | config 파일의 평문 패스워드는 "문서화된 백도어"다. 저장은 암호화, 인증은 일방향 해쉬가 원칙이다. |
| **자세한 설명** | [Part 2-3. 암호화 계열 — 13. 패스워드 평문 저장](개발%20%28CS%29/언어/C언어/시큐어코딩/Part%202.%20보안기능/[시큐어코딩]%202-3.%20암호화%20계열.md#13-패스워드-평문-저장-cwe-256) (Bad/Good 전체 코드, 보충) |

```diff
- void save_password_bad(const char *pw, char *stored, size_t size) { strncpy(stored, pw, ...); }
- int verify_password_bad(const char *stored, const char *input) { return strcmp(stored, input) == 0; }
+ void save_password_good(const char *pw, unsigned *stored) { *stored = toy_hash(pw); }
+ int verify_password_good(unsigned stored, const char *input) { return toy_hash(input) == stored; }
```

## 2. 재현 — 신뢰 경계와 공격 입력

**공격 입력표**

| 저장 방식 | 저장된 값에서 원본 패스워드를 알 수 있는가 | 위험 |
| :--- | :--- | :--- |
| 평문(Bad) | **그대로 보인다** | 설정 파일 하나만 유출되면 패스워드 전체 노출 |
| 해시(Good) | 알 수 없다(단방향) | 유출돼도 원본 복원 불가 |

---

## 3. 주의해야 할 점

1. **`toy_hash` 를 실제 프로덕션 해시로 착각**
	- djb2류 체크섬은 암호학적 해시가 아니다(충돌·역산이 쉽다).
	- 이 드릴은 **저장 구조**(평문 vs 해시)의 차이만 보여준다
		- 실전은 PBKDF2/bcrypt/scrypt/Argon2
1. **SD29(전송)와 SD32(저장)를 같은 문제로 취급**
	- 전송은 양방향(복호화 필요), 저장은 단방향(복호화 불필요, 오히려 안 되는 게 낫다)이 원칙이다.
	- 이 둘을 같은 함수로 처리하면 안 된다

## 4. 변형 (부록)

같은 치환 규칙을 다른 소재로 다시 치는 문제들이다. 저장소에는 변형 A 만 문제로 있다.

### 변형 B — 비밀번호 변경 시 이전 값과 비교

"새 비밀번호가 이전 3개와 달라야 한다"는 요구사항을 해시값만 비교해서 구현(평문 이력을 남기지 않고도 정책을 지킬 수 있음을 보여줌)

### 변형 C — SD33(솔트)과 결합

이 드릴의 `toy_hash` 를 SD33의 솔트 방식과 합쳐, 최종적으로 "솔트+해시" 저장 형태를 완성
