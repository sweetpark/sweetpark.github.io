## 1. 이론 요약

| 항목 | 내용 |
|---|---|
| **신뢰 경계** | 패스워드 → 솔트 없이 → 해쉬 함수 입력 |
| **공격 시나리오** | 솔트가 없으면 동일한 패스워드는 항상 동일한 해쉬값을 만들어, 레인보우 테이블 조회 한 번으로 원본 패스워드가 복원된다. |
| **치환 규칙** | 단순 해쉬(MD5/SHA-1) 금지 → 사용자별 난수 솔트 + PBKDF2/bcrypt/scrypt/Argon2. |
| **주의** | 해쉬는 "되돌릴 수 없다"가 아니라 "미리 계산해 두면 찾을 수 있다"이다. 솔트가 사전 계산을, 반복 횟수가 대량 추측을 막는다. |
| **자세한 설명** | [Part 2-3. 암호화 계열 — 14. 솔트 없이 일방향 해쉬 함수 사용](개발%20%28CS%29/언어/C언어/시큐어코딩/Part%202.%20보안기능/[시큐어코딩]%202-3.%20암호화%20계열.md#14-솔트-없이-일방향-해쉬-함수-사용-cwe-759) (Bad/Good 전체 코드, 보충) |

```diff
- unsigned hash_no_salt_bad(const char *pw) { return toy_hash(pw); }
+ unsigned hash_with_salt_good(const char *pw, unsigned salt) {
+     char buf[128];
+     snprintf(buf, sizeof(buf), "%u:%s", salt, pw);
+     return toy_hash(buf);
+ }
```

## 2. 재현 — 신뢰 경계와 공격 입력

**공격 입력표**

| 상황 | Bad 결과 | 이유 |
| :--- | :--- | :--- |
| alice, bob이 둘 다 `hunter2` 사용 | **완전히 같은 해시값** | 솔트가 없어 입력이 같으면 출력도 같다 → 레인보우 테이블 대조 한 번으로 둘 다 뚫린다 |
| 같은 상황(Good, 서로 다른 솔트) | 서로 다른 해시값 | 사전 계산된 테이블이 무력화된다 |

## 3. 주의해야 할 점

1. **`test_good_normal` 을 빼먹음**
	- 솔트를 섞었다고 해시 함수가 "무작위"가 되면 안 된다.
	- 검증 시점에는 **같은 솔트로 같은 결과**가 나와야 로그인이 가능하다.
	- 이 시험이 그걸 보증한다
1. **솔트를 매번 새로 생성해서 검증 시 다른 솔트를 사용**
	- 저장할 때 쓴 솔트를 검증할 때도 그대로 재사용해야 한다(변형 B에서 `{salt, hash}` 쌍 저장으로 해결)
1. **솔트 값을 아주 좁은 범위(0~9)에서만 고름**
	- 후보가 적으면 솔트별로 레인보우 테이블을 10개만 만들면 되므로 방어 효과가 줄어든다.
	- 실전에서는 128비트급 난수 솔트를 쓴다(SD35와 연결)

## 4. 변형 (부록)

같은 치환 규칙을 다른 소재로 다시 치는 문제들이다. 저장소에는 변형 A 만 문제로 있다.

### 변형 B — 솔트를 해시값과 함께 저장

"솔트는 비밀이 아니다"라는 원칙에 따라, 저장 레코드를 `{salt, hash}` 구조체로 만들어 검증 시 저장된 솔트를 그대로 재사용하는 흐름을 완성

### 변형 C — 반복 횟수(iteration) 개념 도입

`toy_hash` 를 N번 연쇄로 적용하는 "반복" 개념을 추가해, 대량 추측 공격에 걸리는 시간을 늘리는 원리를 체감(PBKDF2의 핵심 아이디어)
