## 1. 이론 요약

| 항목 | 내용 |
|---|---|
| **신뢰 경계** | `access()` 로 검사한 파일 이름 → 그 사이 변경 가능 → `fopen()` 이 실제로 여는 대상 |
| **공격 시나리오** | 검사(time of check)와 사용(time of use) 사이의 좁은 시간차를 노려 자원을 바꿔치기하면,<br>→ 프로그램은 검사에 통과한 것과 다른 대상을 신뢰한 채 다뤄 권한 상승·파일 덮어쓰기로 이어진다. |
| **치환 규칙** | · `access()`+`fopen()` 이름 기반 처리 금지 → 파일 디스크립터 기반으로 열고 그 핸들을 계속 사용<br>· `open(O_CREAT\|O_EXCL)` 로 생성·검사를 원자화<br>· `chmod` 대신 `fchmod`. |
| **주의** | 이름으로 검사하고 이름으로 열지 말라. 검사한 그 핸들을 끝까지 써라. |
| **자세한 설명** | [Part 3. 시간 및 상태 — 1. 경쟁 조건: 검사시점과 사용시점(TOCTOU)](개발%20%28CS%29/언어/C언어/시큐어코딩/[시큐어코딩]%20Part%203.%20시간%20및%20상태.md#1-경쟁-조건-검사시점과-사용시점toctou-cwe-367) (Bad/Good 전체 코드, 보충) |

```diff
- if (!access(file, W_OK))              /* 검사 시점(TOC) — "이름"으로 검사 */
-     f = fopen(file, "w+");             /* 사용 시점(TOU) — 같은 "이름"을 다시 연다 */
+ int fd = open(file_name, O_WRONLY|O_CREAT|O_EXCL, S_IRWXU);  /* 생성과 검사가 한 시스템 콜 안에서 원자적 */
+ if (fd == -1) { /* 이미 존재하면(심볼릭 링크 포함) 무조건 실패 */ }
```

## 2. 재현 — 신뢰 경계와 공격 입력

**신뢰 경계** : 검증 없이 흘러가는 곳

| 값 | 출처 | 검증 없이 흘러가는 곳 |
| :--- | :--- | :--- |
| `path` (파일 이름) | 호출자가 넘긴 경로 | `access()` 로 검사한 뒤 `fopen()` 이 다시 해석하는 대상: 그 사이 이름의 실체가 바뀌어도 알 방법이 없다 |

**공격 입력표**

| 상황 | Bad 결과 | 이유 |
| :--- | :--- | :--- |
| 검사 시점에는 정상 파일을 가리키던 이름이, 사용 시점에는 다른 파일(심볼릭 링크)을 가리킴 | **링크가 가리키는 대상이 그대로 덮어써진다** | `access()`가 "쓰기 가능"을 확인한 건 이름일 뿐, `fopen()`이 실제로 여는 순간 그 이름이 무엇을 가리키는지는 다시 확인하지 않는다 |
| 같은 상황(Good) | **생성 자체가 실패**(`EEXIST`) | `O_CREAT\ | O_EXCL`은 그 이름에 이미 뭔가(파일이든 링크든) 있으면 절대 열지 않는다 |

## 3. 주의해야 할 점

1. **`access()`를 아예 없애기만 하고 `fopen()`은 그대로 둠**
	- 검사를 없애도 `fopen(path, "w+")` 자체가 여전히 이름 기반이라 링크를 그대로 따라간다.
	- 핵심은 검사 제거가 아니라 **생성·검사를 한 시스템 콜로 합치는 것**(`O_CREAT\
	- O_EXCL`)이다
1. **`O_EXCL` 없이 `O_CREAT`만 사용**
	- `O_CREAT`만 있으면 파일이 이미 있어도 그냥 열려버린다(덮어쓰기 성공).
	- `O_EXCL`이 있어야 "이미 있으면 실패"가 보장된다
1. **`chmod(path, ...)`로 권한을 나중에 바꿈**
	- 파일을 연 뒤 이름으로 다시 `chmod`하면 그 사이에 또 이름이 바뀔 수 있다.
	- 이미 연 파일 디스크립터에 대해 `fchmod(fd, ...)`를 써야 한다
