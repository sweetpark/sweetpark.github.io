## 1. 이론 요약

| 항목 | 내용 |
|---|---|
| **신뢰 경계** | 환경변수·내부 경로 → 그대로 → 사용자에게 보이는 오류 메시지 |
| **공격 시나리오** | 공격자는 노출된 경로·환경변수·실패 지점 정보를 조합해 시스템 환경을 정밀하게 수집하고 다음 공격의 정확도를 크게 높인다. |
| **치환 규칙** | 예외 상황은 내부에서 처리하고 사용자에게는 일반화된 단일 메시지만 노출, 상세 내용은 접근 통제된 로그로 분리. |
| **주의** | 상세 에러는 로그(내부)로, 사용자(외부)에게는 단일하고 무의미한 메시지로. 정보 분리가 원칙이다. |
| **자세한 설명** | [Part 4. 에러 처리 — 1. 오류 메시지 통한 정보 노출](개발%20%28CS%29/언어/C언어/시큐어코딩/[시큐어코딩]%20Part%204.%20에러%20처리.md#1-오류-메시지-통한-정보-노출-cwe-209) (Bad/Good 전체 코드, 보충) |

```diff
- snprintf(user_msg, size, "Error: %s", detail);       /* 상세 정보를 사용자에게 그대로 노출 */
+ snprintf(user_msg, size, "요청 처리 중 오류가 발생했습니다.");   /* 사용자에게는 고정된 일반 메시지 */
+ snprintf(log_msg,  size, "[internal] %s", detail);              /* 상세 정보는 로그로만 */
```

## 2. 재현 — 신뢰 경계와 공격 입력

**신뢰 경계** : 검증 없이 흘러가는 곳

| 값 | 출처 | 검증 없이 흘러가는 곳 |
| :--- | :--- | :--- |
| `detail`(환경변수·내부 경로가 섞인 상세 실패 사유) | 내부 로직(`getenv` 등) | 사용자에게 그대로 노출되는 응답 메시지 |

**공격 입력표**

| 상황 | Bad 결과 | 이유 |
| :--- | :--- | :--- |
| 내부 경로가 섞인 실패 사유 발생 | **사용자 메시지에 경로가 그대로 노출** | `snprintf`가 `detail`을 아무 필터링 없이 그대로 사용자 채널에 집어넣는다 |
| 같은 상황(Good) | **사용자에게는 고정 문구만, 로그에는 전체 상세** | 두 개의 출력 버퍼(사용자용/로그용)를 애초에 분리해서 만든다 |

---

## 3. 주의해야 할 점

1. **"정보 노출을 막는다"를 "로그도 지운다"로 오해**
	- 상세 정보를 아예 안 남기면 운영자가 실제 장애를 진단할 수 없다.
	- 막아야 할 건 **사용자에게 보이는 채널**이지 정보 자체가 아니다
1. **사용자 메시지 안에 일부만 가림(예: 경로 앞부분만 마스킹)**
	- 부분 마스킹은 나머지 조각으로도 시스템 구조를 추론할 여지를 남긴다.
	- 아예 무관한 고정 문구로 완전히 치환하는 게 안전하다
1. **로그 버퍼와 사용자 버퍼를 같은 변수 하나로 재사용**
	- 한 버퍼를 순서대로 다른 용도로 덮어쓰면, 나중에 코드가 수정될 때 사용자에게 로그용 내용이 실수로 노출되기 쉽다.
	- 처음부터 별개의 버퍼(채널)로 분리해야 한다

## 4. 변형 (부록)

같은 치환 규칙을 다른 소재로 다시 치는 문제들이다. 저장소에는 변형 A 만 문제로 있다.

### 변형 B — DB 연결 실패 메시지로 변형

`detail`을 "host=10.0.0.5 user=admin ..." 같은 DB 접속 문자열로 바꿔, 노출 시 피해가 더 큰 시나리오를 체감한다

### 변형 C — 오류 코드 매핑 테이블 추가

`detail`을 그대로 로그에 남기는 대신, 내부 오류를 `E1001` 같은 코드로 매핑해 사용자에게는 코드만, 로그에는 코드+상세를 함께 남기는 구조로 확장
