# 시큐어코딩 체화 드릴 _index

> **목적은 "취약점을 아는 것"이 아니다.**
> [시큐어코딩가이드](개발%20%28CS%29/언어/C언어/시큐어코딩/시큐어코딩가이드%20목록.md)의 58개 Bad→Good 치환이 **코드 리뷰 중 3초 안에 손에서 나오게** 만드는 것.
> [템플릿 체화 드릴](개발%20%28CS%29/언어/C언어/실습/템플릿%20체화%20드릴/README.md)이 "요구사항 → 뼈대"를 체화시켰다면, 이 드릴은 **"뚫린 코드 → 막힌 코드"** 를 체화시킨다.
> 그래서 이 폴더의 드릴도 템플릿 체화 드릴과 **같은 방식**(글 + 저장소 문제)으로 이루어진다.
> **글 = 어떤 코드가 뚫리는가 → 치환 규칙 → 뼈대 → 주의점 / 저장소 = 문제 + 채점.**

**문제와 채점은 GitHub 저장소**에 있다 → [sweetpark/c-playgound](https://github.com/sweetpark/c-playgound)
이 폴더의 글은 취약점 개념·치환 규칙·주의점을 담고, 저장소에는 `make P0xx` 로 채점되는 문제(Bad 는 이미 들어 있고 Good 만 구현)를 둔다.
문제 번호는 **`P(45 + SD 번호)`**: SD01 → P046, SD11 → P056, SD58 → P103.

## 이 폴더와 [템플릿 체화 드릴](개발%20%28CS%29/언어/C언어/실습/템플릿%20체화%20드릴/README.md)의 차이

| | 템플릿 체화 드릴 | **시큐어코딩 체화 드릴** (이 폴더) |
| :--- | :--- | :--- |
| 출발점 | 요구사항 한 장 (백지에서 설계) | **이미 뚫려 있는 Bad 코드 한 장** |
| 목표 | 뼈대가 손에서 나온다 | **취약점을 보자마자 치환 패턴이 나온다** |
| 코드 개수 | 정답(Good) 1개 | **Bad + Good 두 벌**: Bad는 취약점이 실제로 관찰돼야 함 |
| 시험 | 정상/경계/NULL 3종 | **Bad 가 뚫리는지 / Good 이 막는지 / 정상은 안 깨졌는지** 4종 |
| 성공 기준 | 뼈대가 10분 안에 나온다 | **Bad 코드를 보자마자 무슨 CWE인지 맞히고, Good으로 고치는 데 목표시간 안에 끝낸다** |

둘 다 "손으로 쳐서 체화한다"는 원칙은 같다.
대신 이 폴더는 정답 하나가 아니라 **대조군(Bad)이 있어야 실감이 난다.**

## 글과 저장소의 역할

| | 글 (이 폴더) | 저장소 |
|---|---|---|
| 담는 것 | 취약점 개념 · 공격 입력표 · 치환 규칙(diff) · 뼈대 · 주의해야 할 점 · 변형 B/C | 문제 한 장 · `solution.c`(Good 만 TODO) · `test.c` · 힌트 · 해설 |
| Bad 코드 | 뼈대에 의사코드로 | 문제 폴더의 `solution.c` 에 **이미 들어 있다** (수정 금지) |
| 모범답안 | 없음 | `solutions/` |

## 재현 전략 — "진짜로 뚫리는 걸 보여줄 수 있는가"

SQL 삽입처럼 실제 DB·LDAP 서버 없이는 취약점을 눈으로 볼 수 없는 항목이 있다.
계열별로 재현 방식을 다르게 쓴다.

| 계열 (Part) | 재현 방식 | 확인 도구 |
| :--- | :--- | :--- |
| 메모리 경계·정수 (1-3·1-4) | **진짜 UB**: 그대로 컴파일하면 실제로 깨진다 | ASan/UBSan이 크래시·오버플로우를 리포트 |
| 삽입 (1-1) | 초소형 mock 파서/실행기를 직접 만들어 "질의·명령·경로의 구조가 바뀌는지"를 눈으로 본다 | assert 기반 자체 테스트 |
| 외부제어·우회, 보안기능(Part 2) | mock 세션/파일/키 저장소 객체로 "판단 근거가 어디 있는지"를 재현 | assert 기반 자체 테스트 |
| 시간및상태, 에러처리, 캡슐화, API오용 (Part 3·4·6·7) | 표준 POSIX 함수 그대로 사용, 실패 주입(모의 실패 콜백)으로 경로를 강제 | assert + 경고 0 |

> [!IMPORTANT] Bad 코드도 "정상적으로 컴파일"되어야 한다
> 여기 Bad 코드는 문법 오류가 아니라 **논리적 결함**이다.
> `-Wall -Wextra -Werror` 를 통과하는 게 오히려 정상이다.
> 메모리 계열은 `expect_crash` 시험이 자식 프로세스의 크래시를 확인해서 "Bad 가 실제로 뚫린다"를 증명한다.
> gcc 가 컴파일 타임에 잡아내는 일부 Bad(SD38 · SD47 · SD49)는 `#pragma GCC diagnostic` 으로 의도적 재현임을 알린다.

## 풀이 방법

| 순서 | 할 일 |
|---|---|
| ① | 이 폴더의 글에서 공격 입력표와 치환 규칙(§1–2)을 읽는다 |
| ② | `make P046` 으로 Bad 가 실제로 뚫리는 시험을 확인한다 (Good 은 아직 FAIL) |
| ③ | `solution.c` 의 Good 을 채워 `PASS` 를 만든다 |
| ④ | 막히면 `HINT1` → `HINT2`, 풀고 나면 `NOTE.md` 와 `make P046 ANS=1` 로 비교 |

- 복습: 같은 문제는 `make reset-P046` 으로 백지로 되돌려 다시 푼다 (보는 것을 줄이며 반복)
- 커밋 메시지: `<문제> r<회차> <소요시간> <결과>` (예: `P046_sd01_sqli r1 12min PASS`)

## 합격 기준 (공통)

| 항목 | 기준 |
|---|---|
| 테스트 4종 | `test_bad_is_vulnerable` / `test_bad_normal` / `test_good_blocks_*` / `test_good_normal` 모두 통과 (`PASS`) |
| 치환 규칙 | 규칙과 다른 방식으로 "우연히" 막은 게 아니다 (예: 길이만 늘림) |
| 정상 동작 | Good 이 정상 입력까지 막지 않는다 (과잉 차단 없음) |
| 빌드 위생 | 경고 **0**, ASan/UBSan **0** |

**`PASS` 가 아니면 통과가 아니다.**
