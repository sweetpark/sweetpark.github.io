# 시큐어코딩 체화 드릴 _index

> **목적은 "취약점을 아는 것"이 아니다.**
> [시큐어코딩가이드](../../시큐어코딩가이드/시큐어코딩가이드%20목록.md)의 58개 Bad→Good 치환이 **코드 리뷰 중 3초 안에 손에서 나오게** 만드는 것.
> [템플릿 체화 드릴](../템플릿%20체화%20드릴/README.md)이 "요구사항 → 뼈대"를 체화시켰다면, 이 드릴은 **"뚫린 코드 → 막힌 코드"** 를 체화시킨다.

**코드는 GitHub repo에서 손으로 친다** → [sweetpark/c-playgound](https://github.com/sweetpark/c-playgound)
이 노트(문제 스펙·회차 규칙·채점표)가 원본이고, repo에는 실제로 타이핑한 `.c`/`.h` 파일만 커밋한다. 드릴 폴더명은 `sd??_이름` (템플릿 드릴의 `d?_이름` 과 같은 자리, `common/` 헤더도 그대로 재사용).

---

## 이 폴더와 [템플릿 체화 드릴](../템플릿%20체화%20드릴/README.md)의 차이

| | 템플릿 체화 드릴 | **시큐어코딩 체화 드릴** (이 폴더) |
| :--- | :--- | :--- |
| 출발점 | 요구사항 한 장 (백지에서 설계) | **이미 뚫려 있는 Bad 코드 한 장** |
| 목표 | 뼈대가 손에서 나온다 | **취약점을 보자마자 치환 패턴이 나온다** |
| 코드 개수 | 정답(Good) 1개 | **Bad + Good 두 벌** — Bad는 취약점이 실제로 관찰돼야 함 |
| 시험 | 정상/경계/NULL 3종 | **공격 입력이 막히는지 + 정상 동작은 안 깨졌는지** 2종 |
| 성공 기준 | 뼈대가 10분 안에 나온다 | **Bad 코드를 보자마자 무슨 CWE인지 맞히고, Good으로 고치는 데 목표시간 안에 끝낸다** |

둘 다 "손으로 쳐서 체화한다"는 원칙은 같다. 대신 이 폴더는 정답 하나가 아니라 **대조군(Bad)이 있어야 실감이 난다.**

## 재현 전략 — "진짜로 뚫리는 걸 보여줄 수 있는가"

SQL 삽입처럼 실제 DB·LDAP 서버 없이는 취약점을 눈으로 볼 수 없는 항목이 있다. 계열별로 재현 방식을 다르게 쓴다.

| 계열 (Part) | 재현 방식 | 확인 도구 |
| :--- | :--- | :--- |
| 메모리 경계·정수 (1-3·1-4) | **진짜 UB** — 그대로 컴파일하면 실제로 깨진다 | ASan/UBSan이 크래시·오버플로우를 리포트 |
| 삽입 (1-1) | 초소형 mock 파서/실행기를 직접 만들어 "질의·명령·경로의 구조가 바뀌는지"를 눈으로 본다 | assert 기반 자체 테스트 |
| 외부제어·우회, 보안기능(Part 2) | mock 세션/파일/키 저장소 객체로 "판단 근거가 어디 있는지"를 재현 | assert 기반 자체 테스트 |
| 시간및상태, 에러처리, 캡슐화, API오용 (Part 3·4·6·7) | 표준 POSIX 함수 그대로 사용, 실패 주입(모의 실패 콜백)으로 경로를 강제 | assert + 경고 0 |

> [!IMPORTANT] Bad 코드도 "정상적으로 컴파일"되어야 한다
> 여기 Bad 코드는 문법 오류가 아니라 **논리적 결함**이다. `-Wall -Wextra -Werror` 를 통과하는 게 오히려 정상이다(단, 메모리 계열은 `check` 단계에서 새니타이저가 의도적으로 실패해야 "Bad"가 증명된다).

## 반복 학습 방법 — 3회차 규칙 (템플릿 드릴과 동일)

| 회차 | 볼 수 있는 것 | 하는 일 | 합격선 |
| :--- | :--- | :--- | :--- |
| **1회차 (모방)** | 드릴 노트 전체 | Bad를 그대로 타이핑 → 빌드 → 취약점 관찰 → Good을 그대로 타이핑 → 재빌드 → 공격 입력이 막히는지 확인 | 빌드 통과 + 공격 시험 통과 |
| **2회차 (재구성)** | **Bad 코드 + 치환 규칙 한 줄만** | Good을 기억해서 친다. 막히면 그때만 모범답안을 연다 | 연 횟수 3회 이하 |
| **3회차 (재현)** | **항목 이름 + CWE만** | Bad부터 Good까지 백지에서 전부 재현 | 목표 시간 안 + 자가채점 90점 |

회차마다 요구사항 컨텍스트를 바꾼다(변형 A/B/C) — 같은 코드를 세 번 베끼면 손이 아니라 눈으로 외운 것이다.

### 간격

```text
D+0  1회차(변형 A)  →  D+1  2회차(변형 B)  →  D+4  3회차(변형 C)  →  D+14  점검(랜덤 변형)
```

---

## 하루 루틴 (25분)

```text
[3분]  드릴 노트 읽기 — 신뢰 경계·⚠️한줄경고 다시 확인
[15분] Bad 타이핑 → 빌드/시험 → Good 타이핑 → 재빌드/시험
[5분]  자가채점표 작성 + 회차 기록표에 시간·점수·막힌 지점 기록
[2분]  커밋 (아래 컨벤션)
```

---

## repo 사용법 (sweetpark/c-playgound)

```bash
make D=sd01_sqli T=main        # 빌드 + 실행
make D=sd01_sqli T=main check  # 경고 0 + 새니타이저 0(또는 의도된 실패) 검사
```

커밋 컨벤션은 템플릿 드릴과 동일 — **같은 파일을 덮어쓰고 커밋**해 git log가 회차별 변화(Bad만 있음 → Bad+Good → 백지 재현)를 보여주게 한다.

- 커밋 메시지: `<드릴> r<회차>(<변형>) <소요시간> <자가채점점수>`
  예: `sd01_sqli r1(A) 12min 90pt`
- 1회차는 Bad와 Good을 **분리 커밋**해도 좋다(`sd01_sqli r1-bad(A) ...` → `sd01_sqli r1-good(A) ...`) — diff 자체가 치환 규칙을 보여주는 기록이 된다.

## 자가 채점 공통 기준 (100점)

| 항목 | 배점 | 0점 처리되는 경우 |
| :--- | :--- | :--- |
| **취약점 식별** | 20 | Bad 코드에서 신뢰 경계 위반 지점을 못 짚었다 |
| **Bad 재현** | 15 | Bad 코드가 의도한 방식으로 실패/오탐지되지 않는다(취약점이 실제로 안 뚫린다) |
| **Good 치환 정확도** | 25 | 치환 규칙과 다른 방식으로 "우연히" 막았다(예: 길이만 늘림) |
| **정상 동작 보존** | 15 | Good이 정상 입력까지 막아버린다(과잉 차단) |
| **시험 2종 통과** | 15 | 공격 입력 차단 시험 또는 정상 동작 시험 중 하나라도 없다 |
| **빌드 위생** | 5 | 경고 1개라도 있다(메모리 계열은 Good 단계 기준) |
| **시간** | 5 | 목표 시간의 2배 초과 |

**90점 미만이면 그 회차는 통과가 아니다.**
