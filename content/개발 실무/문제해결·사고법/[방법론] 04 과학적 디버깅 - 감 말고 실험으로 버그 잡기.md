# 과학적 디버깅 - 감 말고 실험으로 버그 잡기

> [!NOTE] 한 줄 요약
> 프로그램이 이상할 때는 **"이럴 것 같다 → 실험해서 확인 → 맞으면 고치고, 틀리면 다음 가설"** 순서로 간다.

## 디버깅이 뭐예요?

프로그램의 오류를 **버그**라고 하고, 그걸 찾아 고치는 일을 **디버깅**이라고 해요. 이때 가장 위험한 건 **"여기가 문제인 것 같은데?" 하고 이것저것 막 고치는 것**이에요.

고장 난 리모컨을 생각해 보세요. 건전지도 갈고, 버튼도 누르고, 케이스도 열고 한꺼번에 하면 나중에 리모컨이 고쳐져도 **뭐가 원인이었는지 모르죠.**

## 과학 실험처럼 하기

과학 시간에 하던 "가설 → 실험 → 결과 → 결론"을 그대로 써요.

| 순서 | 할 일 | 리모컨 예시 |
|---|---|---|
| 1. 재현 | 문제가 **항상** 생기는 조건 찾기 | "TV 켜기 버튼만 안 눌려요" |
| 2. 관찰 | 기대한 것 vs 실제, **사실만** 적기 | 기대: 켜짐 / 실제: 반응 없음 |
| 3. 가설 | "원인은 X일 것" (**틀렸음을 확인할 수 있게**) | "건전지가 약해서 일 것" |
| 4. 실험 | 맞다면 어떤 결과가 나올지 **예측**하고 확인 | 새 건전지를 넣으면 켜질 것 |
| 5. 결론 | 맞으면 수정, 틀리면 다음 가설. **한 번에 하나만** 바꾸기 | 안 켜짐 → 가설 기각 |
| 6. 검증 | 고쳐졌는지, 다른 게 안 깨졌는지 확인 | 다른 버튼도 되는지 확인 |

## 메모 양식

```
기대 동작:
실제 동작:
재현 조건:
가설 1:      예측: 맞다면 ~가 보일 것
실험 1:
결과 1:      → 채택 / 기각
수정 내용:
검증 결과:
```

## 범위를 좁히는 요령

- **반으로 나누기(이분 탐색)**: 잘 되는 지점과 안 되는 지점 사이의 중간에 확인용 기록을 넣어요. 숫자 맞히기 게임에서 "50보다 커?" 하고 반씩 줄이는 것과 같아요.
- **최근에 뭐 바꿨지?**: 언제부터 이상해졌는지 변경 기록을 살펴봐요. (`git log`, `git bisect`)
- **잘 되는 경우와 비교**: 입력, 상태, 환경 중에서 **뭐가 다른지** 찾아요.

## 조심할 점

- **한 번에 하나만** 바꾸세요. 여러 개 바꾸면 무엇이 효과였는지 알 수 없어요.
- **틀린 가설도 기록**하세요. 같은 길로 또 들어가지 않으려고요.
- "고친 것 같다"로 끝내지 말고 **고쳐졌다는 증거**를 확인하세요.

## 정리

- 감으로 고치기 ❌ / 가설 세우고 실험하기 ✅
- 한 번에 하나씩, 결과는 기록, 마지막엔 검증!
