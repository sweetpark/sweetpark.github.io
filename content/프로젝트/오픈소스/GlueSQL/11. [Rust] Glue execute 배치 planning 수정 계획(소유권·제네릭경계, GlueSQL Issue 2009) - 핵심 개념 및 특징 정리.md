# Glue::execute 배치 planning 수정 계획 (소유권·제네릭 경계, GlueSQL #2009)

> [!NOTE]
> 아직 착수 전 — 이번 주 일요일 작업 예정. 세 후보 중 가장 범위가 크고(파일 하나, 함수 두 개) 제네릭 트레잇 경계(`T: GStore + GStoreMut + Planner`)를 직접 다루게 됨. 이슈 본문에 수정 방향과 테스트 코드까지 이미 적혀 있어서 "이해하고 내 손으로 옮겨 쓰기"에 좋은 난이도.

## 📌 개념

### 문제 — 한 번에 여러 SQL 문을 실행하면, 뒤 문장이 앞 문장의 DDL을 못 봄

```sql
CREATE TABLE S;
INSERT INTO S VALUES ('{"a": 1}');
SELECT a FROM S;
```

이 세 문장을 **한 번의 `glue.execute(...)` 호출**에 세미콜론으로 이어 붙이면 `identifier not found: a` 에러가 남. 반대로 한 문장씩 세 번 나눠 호출하면 정상 동작. "여러 문장을 한 번에 실행하는 것"과 "한 문장씩 실행하는 것"의 결과가 달라지면 안 되는데 다름.

### 원인 — 전부 plan 하고 나서야 실행이 시작됨

`core/src/glue.rs`:

```rust
// execute_with_params (현재)
pub fn execute_with_params(&mut self, sql, params) -> Result<Vec<Payload>> {
    let statements = self.plan_with_params(sql, params)?;  // 여기서 SQL 전체를 먼저 다 plan
    let mut payloads = Vec::new();
    for statement in &statements {
        payloads.push(self.execute_stmt(statement)?);       // 그 다음에야 하나씩 실행
    }
    Ok(payloads)
}
```

`plan_with_params`는 내부에서 `parse(sql)?`로 나온 모든 문장을 `.map(...).collect()`로 한 번에 planning함. 두 번째 문장(`SELECT a FROM S`)을 planning하는 시점엔 아직 첫 번째 문장(`CREATE TABLE S`)이 실행 전이라 스키마 맵에 `S`가 없음 → planning 단계에서 스키마를 보는 최적화/검증 패스들이 전부 "테이블 없음"으로 조용히 스킵되거나 잘못된 결과를 냄.

### 고쳐야 하는 pseudocode

이슈 본문에 정확한 방향이 이미 제시돼 있음 — **plan과 execute를 문장 하나 단위로 묶어서 반복**:

```rust
// core/src/glue.rs — execute_with_params 수정 방향
pub fn execute_with_params<Sql, I, P>(&mut self, sql: Sql, params: I) -> Result<Vec<Payload>>
where
    Sql: AsRef<str>,
    I: IntoIterator<Item = P>,
    P: IntoParamLiteral,
{
    // params 변환은 문장마다 반복할 필요 없이 루프 밖에서 한 번만
    let params: Vec<ParamLiteral> = params
        .into_iter()
        .map(IntoParamLiteral::into_param_literal)
        .collect();

    let mut payloads = Vec::<Payload>::new();
    for p in parse(sql)? {
        let statement = translate_with_params(&p, &params)?; // params는 빌려서(&) 씀
        let plan = self.storage.plan(statement.into())?;
        payloads.push(self.execute_stmt(&plan)?);             // 바로 실행 → 다음 반복의 planning이 이 결과를 봄
    }
    Ok(payloads)
}
```

- **`Glue::plan`(prepared-statement 진입점)이 쓰는 `plan_with_params`는 그대로 둔다** — 이건 "실행 전에 전부 미리 계획만 해두고 싶은" 용도라 지금 동작이 맞음. 손대는 건 `execute_with_params`뿐.
- **동작 변경 하나 인지**: 이제 배치 중간 문장에서 planning 에러가 나면, 그 앞 문장들은 이미 실행된 채로 끝남(이전엔 첫 문장부터 하나도 실행 안 되고 에러). 이슈 본문도 이걸 "의도된 동작 변화"로 명시함.

### 손으로 확인해볼 포인트 (소유권 관점)

- 기존 코드는 `plan_with_params`가 `params: I`를 통째로 소비해서 `Vec<ParamLiteral>`을 한 번만 만들고 끝. 고친 코드도 **루프 진입 전에 딱 한 번** `Vec<ParamLiteral>`로 변환해두고, 루프 안에서는 `&params`로 매 반복 "빌려서" `translate_with_params`에 넘김 — 왜 루프 안에서 매번 새로 만들면 안 되는지(애초에 `I: IntoIterator`는 한 번만 소비 가능) 생각해보기
- `parse(sql)?`가 반환하는 값을 `for p in ...`로 바로 순회 — 기존처럼 `Vec`에 다 모았다가 순회하는 것과 무엇이 다른지(모아두지 않고 바로바로 쓴다는 점에서 "즉시 실행"이 가능해짐)

### 테스트 방법

이슈 본문에 이미 테스트 코드가 통째로 있음 — `pkg/rust/tests/glue.rs`에 적용:

1. `fn batch<T: GStore + GStoreMut + Planner>(glue: &mut Glue<T>)` 함수 추가 — 이슈에 적힌 두 케이스(스키마리스 배치 + JOIN ambiguity 배치) 그대로 옮겨 적기
2. 기존 `basic`이 `Glue<T>`를 값으로 받던 걸 `&mut Glue<T>`로 바꿔서, 하나의 `glue` 인스턴스로 `basic` + `batch`를 이어서 호출 가능하게 함
3. 기존 `memory_basic`/`sled_basic`을 `memory`/`sled`로 이름 바꾸고 그 안에서 `basic(&mut glue); batch(&mut glue);` 순서로 호출
4. `cargo test -p gluesql --test glue`
5. `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --all`

> [!NOTE]
> `sled_basic`은 `data/using_config` 경로를 고정으로 씀 — 이슈 본문이 "같은 경로를 또 여는 별도 테스트를 만들면 병렬 테스트 실행 중 경합(race)이 날 수 있다"고 경고함. 새 테스트를 따로 만들지 말고 기존 `sled`(구 `sled_basic`) 함수 안에서 이어서 호출해야 하는 이유.

### 배울 Rust 개념

- **소유권과 참조**: `Vec<ParamLiteral>`을 루프 밖에서 한 번 소유(own)하고 루프 안에서는 참조(`&params`)로만 빌려쓰는 패턴
- **트레잇과 제네릭 경계**: `Glue<T: GStore + GStoreMut + Planner>`처럼 여러 트레잇을 한 타입 파라미터에 동시에 요구하는 경계, 테스트 헬퍼 함수도 같은 경계를 그대로 반복
- **이터레이터**: `parse(sql)?`(문장들의 iterator)를 `Vec`로 모으지 않고 `for` 루프로 즉시 소비하면서 매 항목마다 부수효과(실행)를 내는 스타일 — "모아서 처리" vs "받는 대로 처리"의 차이
